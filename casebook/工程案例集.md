## 一、CSS 与组件

### C1 同一属性被四层规则反复覆盖，最后生效的不是「最新改的那处」
- **现象**：普通用户顶栏塌成 64px 白块压在品牌上；侧栏宽度 232px 与硬编码 220px 并存，1180px 断点的 `204px` 早已失效。
- **根因**：同一断点下叠了 4 段框架规则（「桌面应用框架」「首页方案 A」「方案 A 应用框架」「框架对齐收口」共 408 行），后写的块完整覆盖前块，但前块的遗留属性（如 `backdrop-filter`）仍在生效。
- **规避**：框架样式只留一个出处（新建 `public/sidebar.css`），宽度只由 `--sidebar-w` 决定；改动前先 `grep` 属性与旧选择器，删除失效块而不是继续叠加。
- **适用场景**：无构建、长期多人迭代的 CSS；任何「样式改了不生效」的排查。

### C2 backdrop-filter 非 none 的祖先会成为 fixed 后代的包含块
- **现象**：普通用户顶部账号栏 `.user-area` 宽度塌缩为 64px（只剩左右 padding）并向左溢出；管理员布局正常。
- **根因**：一段已被完全覆盖的历史规则残留 `backdrop-filter: blur(14px)`，而它是 `position: fixed` 元素（`inset: 0 0 auto 220px`）的祖先 → 包含块由视口变成 220px 宽的侧栏，`left 220 + right 0` ⇒ 内容宽 0。
- **规避**：在最终生效的块显式声明 `backdrop-filter: none` 并附根因注释；定位 fixed 元素异常时先查全部祖先的 `filter` / `transform` / `backdrop-filter` / `contain`。
- **适用场景**：任何 CSS + fixed 浮层；毛玻璃遮罩/顶栏组件最常见的布局陷阱。

### C3 组件内部布局：插槽决定排列，`--sl-input-height-*` 决定高度
- **现象**：侧栏账号按钮内容纵向堆叠、被撑到 79px；导航按钮实测 54px 高，窄屏顶栏被撑到 134px（占手机屏 1/6）。
- **根因**：① 头像/文字/箭头全投默认插槽，而组件内部只有 prefix / label / suffix 三个 flex 子项，默认插槽不是 flex 容器；② 只写 `height: 48px` 没改 `--sl-input-height-medium`，内部行高仍按 38px 算；③ 在 `::part(base)` 加 `padding: 8px 14px` 会与按变量算出的 `line-height` 叠加成 54px。
- **规避**：内容按插槽语义分派（prefix / suffix / label）；高度只改组件的高度变量；先量 `getBoundingClientRect().height` 再改；把「同档位控件等高」（筛选 40 / 表格按钮 30 / 导航 36 / 账户 40）写成断言。
- **适用场景**：Web Components / shadow DOM 组件的高度与内容布局。

### C4 `await dialog.show()` 会把后续逻辑一起卡死
- **现象**：抽屉打开了，内容却永远停在「正在加载」——数据请求压根没发出去。
- **根因**：`show()` 要等 Web Animations 入场动画结束才 resolve，无合成帧环境（无头浏览器、后台标签页）动画永不结束 → Promise 永远 pending；同一根因让挂在 `requestAnimationFrame` 上的组件初始聚焦也不执行。
- **规避**：一律 `void dialog.show()`，绝不在它上面 await；焦点自己接管（拦 `sl-initial-focus` + `updateComplete` 兜底）。凡是「等组件动画」的 await 都要怀疑一遍。
- **适用场景**：无头/后台标签页、E2E 与定时任务中操作浮层组件。

### C5 自定义元素不是原生表单控件
- **现象**：`form.elements.xxx` 取不到值（length 0）、`el.disabled = true` 不生效、只派发 `sl-change`、刚插入文档就 `.focus()` 抛 null、shadow DOM 里回车不提交；另有 `sl-after-hide` 冒泡，弹窗内下拉收起被误判成「弹窗已关闭」→ 新建账号一选角色弹窗就消失。
- **根因**：Web Components 的表单语义、事件模型、属性驱动、异步渲染都与原生控件不同；冒泡事件会被浮层收尾监听器当成自身事件。
- **规避**：全部封进 `uiKit` 适配层（`fieldValue` / `setDisabled` / `onValueChange` / `focusWhenReady` / `enterSubmits`）；浮层监听器加 `if (event.target !== 自身) return`。注意 `FormData` 与 `sl-button[type=submit]` 是正常工作的，别凭直觉一起改。
- **适用场景**：任何引入 Web Components 的原生 JS 项目。

### C6 多选控件被选中项撑高，顶掉整行对齐
- **现象**：「当前状态」全选 6 项时控件 40px → **145px**、筛选表单 94px → **199px**。
- **根因**：`.select__tags` 是 `flex-wrap: wrap`，控件宽 135px 而单个标签 87px → 一行只放 1 个、4 个标签排 4 行；组件 `max-options-visible` 默认 3，标签数随选中项增长；外层 grid 是 `align-items: end`，同行任一控件变高就顶起整行。
- **规避**：`max-options-visible = 1`（只平铺 1 个标签 +「+N」）+ 按 size 三档锁 `max-height` + `::part(tags)` 强制 nowrap；用「7 个视口 × 选中 0/1/2/3/6 项恒 40px、标签零裁切」做断言。
- **适用场景**：多选下拉 / 标签输入类组件；所有「高度随内容变化」的筛选区。

### C7 字体：声明了没加载的 Web 字体、等宽缺中文回退、字号字重发散
- **现象**：不同机器字形与粗细不同；全站 22 种字号取值；`font-weight` 出现 650(×27)/750/800/900；数字列宽随内容跳动。
- **根因**：字体栈首选 `Inter` 但项目从未加载（装了它的机器走 Inter，没装的走 PingFang）；`--font-mono` 无中文字体回退，Windows 上中文落到宋体；非标准字重被静态字体就近取整或**合成加粗**；只有 `.stat-value` 有 `tabular-nums`。
- **规避**：字体栈只写本机真实存在的字体 + 等宽栈显式带中文回退；字号收敛 **22 档 → 8 档**、字重 **6 档 → 4 档**并全量 token 化；`strong/b` 显式 `font-weight` 挡掉 `bolder` 叠加；编码与时间统一 12px 等宽 + `tabular-nums`。
- **适用场景**：跨平台交付的内部系统；设计 token 化改造。

### C8 尺寸必须有唯一出处，且承载容器要能被压窄
- **现象**：1440px 下首页表格已横滚（目标列宽合计 **1177px > 可用 1154px**）；1920px 下「操作」列被撑到 **525px** 而只放一个按钮；全站输入框宽 132–1080px 十几种取值；固定 320px 后第一版控件溢出所在列 **36px**。
- **根因**：列宽/输入宽没有单一来源——`td` 上的 `min-width` 会顶开 `colgroup`、`width: 100%` 让宽度由容器决定、`table { width: 100% }` 时浏览器会忽略 `max-width` 去铺满；固定宽控件放进 `minmax(0, 320px)` 的列会被 grid 压窄。
- **规避**：列宽只来自列定义（`colgroup`）+ 仅用于下限的 `min-width`，超宽屏（≥1700px）让某一列吸收余量；输入宽只由 `--input-width` 决定，网格一律 `repeat(auto-fill, minmax(min(100%, var(--input-width)), var(--input-width)))` 并给字段容器 `min-width: 0`；主值 `line-clamp` 限行、完整值放 `title`；首列固定必须有不透明底色、空态行显式取消 sticky。
- **适用场景**：数据密集表格 + 固定控件宽度的后台系统。

### C9 局部刷新：只重绘该重绘的，并让过期响应失效
- **现象**：早期每次筛选/翻页整页重绘 → 输入框失焦、滚动跳动；快速连点时先发的慢响应覆盖后发的结果；局部刷新后新鲜度、同步进度等区域没人更新。
- **根因**：重绘范围过大、没有请求竞态处理、需要同步更新的区块没有可替换的锚点。
- **规避**：只重绘统计卡与表格卡片，筛选面板不重建；用递增请求序号丢弃过期响应；轮询定时器挂进 `layoutCleanup`；随局部刷新变化的区块给固定 id（如 `#sync-freshness`）；进度完成摘要先显示、1.2 秒后再重绘列表。
- **适用场景**：原生 JS 看板/列表页；任何「刷新后丢了焦点与滚动」的界面。

## 二、数据与口径

### D1 「未签收」在概览卡与筛选里是两个定义
- **现象**：点「未签收」卡片，列表条数与卡片数字对不上——卡片 **15**，`?signed=false` 返回 **173**。
- **根因**：卡片用 `is_signed = 0 AND is_placeholder = 0`（PRD L114「全部未签收**且带快递单号**」），而列表 `signed=false` 只过滤 `is_signed = 0`，把 158 票「待填写单号」的占位单也算成未签收；占位单（无单号）与未签收本是两个独立维度，纠缠后数字必然打架。
- **规避**：口径只保留一处实现；把「卡片值 = 对应筛选的 total」写成断言（改前 actual 2 / expected 1）；三态互斥写进用例（未签收 15 + 待填写 158 + 已签收 38 = 全部 211）；`signed=false&pending=true` 这类自相矛盾查询明确返回空集；旧链接参数保留折算以兼容外部调用。
- **适用场景**：任何「概览数字可点即筛选」的看板；占位/无效记录与真实业务状态混存的系统。

### D2 用单据级 ID 当行主键，多行明细整单入库失败
- **现象**：每轮同步固定 **41 条**发货单入库失败（不是限流），这些单既没有明细也没有采购信息。
- **根因**：`order_items` 的行主键用了上游 `fid`/`id`，而它们是**单据级** ID（同一交货单 6 行明细的 `fid` 全是 `54331`），行级唯一的是 `poItemId` → 撞 `UNIQUE(erp_order_id, line_key)`；外层 `catch {}` 又静默吞错，只累加计数，无从诊断。
- **规避**：行主键改用行级 ID（`poItemId`/`lineId`）+ 数组下标兜底 + 交货单号前缀双保险；`catch` 记录失败单号与原因样本（最多 10 条）随结果返回。修复后 `processedCount 123 → 164`、`failedCount 41 → 0`。
- **适用场景**：所有从上游「单据 + 明细」结构落库的同步任务。

### D3 结构化字段不等于干净值（快递公司名 + 单号混在一串）
- **现象**：库里 **224 条**单号形如 `S66565296289顺心捷达`，交给快递100 一律 `400 单号不是数字和字母组合`——页面上它们看起来「有单号」，问题被完美掩盖。
- **根因**：字段路径写成 `let trackingNo = field` 原样返回，只有备注路径才过提取引擎；上游 `trackings` 实测就是「公司名 + 单号」混串（`联昊通\t906571425039`、`诚旭物流：21121284`、`奥欣物流 5014235`）。
- **规避**：结构化字段也当外部输入，取值后先校验形态；判断标准落在「**有没有非单号字符**」（`/^[A-Za-z0-9][A-Za-z0-9-]*$/`）而不是长度（按长度会把 `SF1` 这类短单号误送进提取引擎，第一版修复就栽在这）；不采信前缀猜出的公司名，公司名从原文提取；历史脏值单独迁移（清洗 **129 条** + 合并 **10 组**，`erp_orders` 2524 条关联零丢失）。
- **适用场景**：所有对接上游 ERP / 开放平台的数据清洗。

### D4 关联 / join 靠「想当然」，0 命中也不报错
- **现象**：运营/站点/部门三列长期全空；旧链路实测 `明细 seller_sku = ref_msku.msku` **0/116**、`managerAccount = username` 314/7728、`shop_id = market.id` **0/539**。
- **根因**：SQLite 的 LEFT JOIN 在列不存在或值体系不同时不报错、只返回 null；上游 `msku` 是另一套编码（`S02452`）且 `productManagerAccount` 返回中文姓名而非账号。同类误判还有：用 `erp_orders.id`（自增）去 JOIN `order_items.erp_order_id`（业务 `erp_id`），得出「428 条明细全是孤儿」，真孤儿为 0。
- **规避**：先确认上游**哪个接口真的同时返回这两个字段**再写 join；用「资料已同步」的用例断言出具体人名/站点；改链后给出命中率（`product → products.sku` **108/108**、`姓名 → users.name` **7728/7728**、能关联出运营+部门的明细 96/108）；写 join 前核对列语义，不靠列名相似。
- **适用场景**：多源数据关联、资料表与业务表拼接。

### D5 幂等合并时先删父行，会把整票单据一起级联删掉
- **现象**：占位单补上真实单号后走「合并」分支，占位单上的**全部单据被删**，而调用方只重建当前一条。
- **根因**：`erp_orders.shipment_id` 是 `ON DELETE CASCADE`，而 `promotePlaceholderShipment` 的冲突分支直接 `DELETE FROM shipments`；同一单号多票占位（`500284649696` 3 票、`800220897594` 4 票）正好走这个分支。
- **规避**：在事务内先把 `erp_orders` 批量改指目标运单、再删占位行；补数脚本默认 dry-run，先确认会不会走合并分支（本次因此「先修缺陷、再跑补数」）；去重靠 `UNIQUE(tracking_no)` 驱动合并，而不是直接 UPDATE。
- **适用场景**：有外键级联的库 + 任何「占位/临时记录升级为正式记录」的流程。

### D6 页面上「这列没数据」可能是聚合取错字段，或被排序挤走了
- **现象**：产品列整列显示「—」（有明细的 164 票里 **22 票**如此）；同步完成后「快递/状态/最新轨迹/更新」看着全空，首页 20 行全是「待填写快递单号」。
- **根因**：① `asin_list` 只收集 `item.asin`，而采购类明细（原料/辅料/包装）本就没有 ASIN → 前端 `if (asins.length)` 不成立，整个产品区块（含运营/站点/部门）都不渲染；② 排序把没有 `last_track_at` 的占位行退回 `updated_at` 比较，它们刚同步完时间最新，把有轨迹的记录全挤到后面。
- **规避**：聚合值做回退链（`asin → product_name → seller_sku → product`，并补查所需列）；空态给一句说明而不是整块消失；排序把占位行沉底（`is_placeholder ASC` 放在首位）；用户反馈「字段是空的」时先查排序与数据事实，再怀疑渲染。
- **适用场景**：列表聚合列 + 分页排序；上游字段缺失率高的数据源。

## 三、同步与外部接口

### S1 上游限流是「限频率」不是「限总量」
- **现象**：基础资料接口持续 `HTTP 509 / code 90008`「接口调用次数已超过限制次数」，被判断成「当日额度用尽、等次日恢复」；而 ERP 主同步（50 次分页）能成功、并发打出的 5 个资料接口必挂。
- **根因**：真实规则是**每 1 秒 2 次**；`Promise.all` 并发直接绕过单次间隔限制，连续调用太密才被限流，与总量无关（认知错误导致方向整体跑偏）。
- **规避**：全局限速（`minIntervalMs = 600ms`，留 20% 余量）+ 识别 `90008`/`509`/「超过限制次数」文案 + 指数退避（`retryBaseMs 1000`，1s→2s→4s）+ 并发改**串行**；用本地 mock 上游验证退避（前两次 509、第三次成功；一直 509 则重试耗尽后报错且信息里能看出是限流）。
- **适用场景**：所有对接第三方开放平台的同步器。

### S2 别为要丢弃的数据付接口调用成本
- **现象**：为了 176 条有用数据拉了 **2500 条**，预计 **~75 分钟**；明细是逐单调用，若不预判就要为 **2342 条**注定丢弃的记录白打两千多次接口。
- **根因**：筛选只在本地做（上游参数名未知），先全量拉再过滤；明细接口一次只接受一个单号。
- **规避**：先探测服务端筛选参数（`transportList=['113']`、`statusList=['draft','picking','shipped','receiving']` 英文码；`transportName`/`transportCode`/`status`/`statusList=[1]` 实测无效，记下来别再试），筛选下推后 2500 → **176** 条、列表调用 50 → **4** 次、~75 分钟 → **~6 分钟**；预判与落库共用同一份判据（`src/orderFilter.mjs`），本地过滤保留为兜底而不是主力。
- **适用场景**：分页拉取 + 本地过滤的同步任务；逐单调用的明细接口。

### S3 两轮同步并发跑：进度回退、重复消耗额度
- **现象**：进度从「发货单：94 / 176 · 已用 43 秒」退回「20 / 176 · 已用 **43 秒**」——两次秒数完全相同是决定性线索；数据库里同时有 2 条「运行中」同步记录（历史上还有 3 条同时在跑）。
- **根因**：手动「立即同步」撞上定时同步（或重复点击），两轮**共用一个全局进度对象**交替写入；危害不止显示错乱，还包括重复消耗积加调用与快递100 额度、并发写同一个 SQLite。
- **规避**：用 in-flight Promise 作互斥（`withLock`），第二轮立刻返回 `skipped` 而不排队干等；前端拿到 `skipped` 不假装「同步完成」；用「mock 上游故意拖慢 150ms 制造并发窗口 → 有且仅有一轮被跳过、上游只被调用一次」做断言。
- **适用场景**：有定时任务 + 手动触发入口的单进程服务。

### S4 外部接口 401：手填令牌短路、重试只写一半路径、错误体被丢弃
- **现象**：定时器每 20.0 分钟精确跑一轮（累计 **698 轮**）但每轮都失败，数据冻结 2 天，日志里只有一行 `sync_runs` 失败；另有 **43.8 小时**完全无同步记录（`setInterval` 不补跑错过的轮次）。
- **根因**：① `ensureAccessToken` 首行 `if (accessToken) return`，手填令牌永久短路自动换取，24 小时过期后每轮 401，而重试条件写成 `!accessToken`，连兜底重试也不生效；② 重试逻辑只写在「HTTP 200 + 业务码」分支、正则只匹配「鉴权失败」，真实形态是 `HTTP 401 + code 40005 +「token已失效」`→ 第一次修复线上完全没触发；③ `erpFetch` 在 `!response.ok` 时直接抛「HTTP 401」并丢弃响应体，用户只能反复猜；④ 换取令牌路径默认值多拼一段 `/api/open`（基地址已含），拼成 `.../api/open/api/open/api_token` 被网关拒成 401。
- **规避**：手填令牌被上游拒绝后**永久回退** AppId+AppKey 自动换取；重试判定在「非 2xx」与「200+业务码」两条路径共用；一律先 `response.text()` 再判状态并透出上游 `code`/`messages`；对配置错配直接拦截（积加域名 + 非积加鉴权在保存与测试连接时就拒）；按真实响应形态写测试。
- **适用场景**：带令牌自动续期的第三方 API 接入；「只修了一半的兜底逻辑」。

### S5 快递公司识别错：候选来源不该只有一个
- **现象**：3 票 14 位 `7903…` 单号每轮失败、累计重试 **37 次**（按 30 分钟一轮约合一天 96 次无效查询）；用识别结果 `zhongtong` 查询报 `408 验证码错误`，换 `zhongtongkuaiyun` 成功。
- **根因**：这 3 票属中通**快运**，而识别接口只给 1 个候选（中通**快递**，两家不同公司）；ERP 原值里其实写明了公司名（`中通快递：…`、`中通快运 …`）并已提取进 `courier_name`，但只用于展示、没有映射成查询用的 `courier_code`。
- **规避**：候选队列 = 识别结果 → ERP 公司名映射 → 同族编码扩展（去重、有界），只在「公司参数异常」类错误时换下一个；408 归因改为「优先怀疑 com 编错公司」；失败单加最小重查窗口（6 小时冷却：冷却期内退出队列、窗口结束后仍优先重试）；同族编码必须**实测确认存在**再写进映射表。
- **适用场景**：上游识别类接口 + 多家承运商编码体系。

### S6 返回格式取决于请求参数；状态判定不能只看顶层码
- **现象**：报错「快递100 接口返回错误（错误码 无）：ok」；正常派件中的快件被标成运输异常（违反 PRD AC-005）。
- **根因**：带 `show` 参数时快递100 返回 **XML**、不带才返回 JSON（原实现只认 JSON，把成功 XML 报成错误）；顶层 `state=2`「疑难」与最新轨迹节点 `status`「派件」不一致，按顶层判就把正常派件标成异常。
- **规避**：同时支持 XML/JSON 与 `{ success, error_msg, track_data }` 外层包装；状态优先级固定为「最新节点 status → `ischeck=1` → 顶层 state → 文本正则」；智能识别的凭据用 `key` 而不是 `customer`（传 customer 返回 `601 key过期`）；把「接口失败不得覆盖最近一次有效状态」写成用例。
- **适用场景**：同一接口多返回格式的上游；「上游码表与明细节点冲突」的状态归一。

## 四、进程与部署

### P1 服务监听 0.0.0.0 + 匿名接口回显演示口令
- **现象**：`/api/health` 对任何来源都回显 `demo/****`，同网段任何人一个匿名请求即可拿到**可用管理员凭据**（已实测用泄漏口令登录成功并可读写 `/api/admin/settings`）。
- **根因**：为方便本地开发把演示账号写进 health；服务绑定 `0.0.0.0`；来源判断只想到「是不是本机」。
- **规避**：口令类信息只对回环来源回显（IPv4 回环是整段 `127.0.0.0/8`，双栈下还会呈现为 `::ffff:127.x`，要按前缀判断）；反向代理后 `socket.remoteAddress` 会变成 `127.0.0.1` 使判断退化为「总是本机」，因此生产必须配 `APP_USERNAME/APP_PASSWORD` 从根上不走演示分支；用局域网地址（192.168.x）写「取不到口令」的用例并确认 `skipped=0`。
- **适用场景**：内网部署；演示/开发便利功能上生产。

### P2 没有隔离的失败会一路冒泡：进程起不来、核心阶段被跳过
- **现象**：空库首次启动时 ERP 同步成功后「基础资料」抛错，进程 **exit 1**、端口 3000 始终不监听——上游一次限流就让服务完全起不来；另一处表现为「物流单正常入库，但一条轨迹都没有」。
- **根因**：启动引导同步是**顶层 await 且无 try/catch**（同一程序的定时同步有 `.catch()`，唯独这处没有）；`syncAll` 里 `await syncReference()` 排在 `await syncTracking()` 之前，资料接口 509 抛错直接跳过轨迹查询。
- **规避**：给启动引导包 try/catch 并照常 `server.listen()`（带着旧数据先起来）；同步改**阶段级容错**（任一阶段失败只收进 `failures` 不中断，轨迹阶段始终执行）；改完容错后必须显式检查 `result.failures` 记日志，否则「ERP 鉴权失效」这类故障只剩 `sync_runs` 表里一行、日志彻底静默；用「ERP 配置成已启用但地址不可达 + 清空 shipments」复现「仍能监听」。
- **适用场景**：单进程常驻服务；多阶段流水线（同步 / ETL / 构建）。

### P3 「我改了你怎么没变化」：先分清后端没重启还是前端被缓存
- **现象**：用户反馈「刷新页面没有变化」；新列与新排序表现为「点了没反应」。
- **根因**：`node src/server.mjs` 是常驻进程不是 `--watch`（`src/` 改动不重启不生效）；`index.html` 里写死 `/app.js`，无法自证用户加载的是哪一版；改字段默认值对已有存量配置也无效。
- **规避**：服务端响应 `index.html` 时把资源地址改写为 `?v=<mtime>`，并在页面上显示界面版本，让「我改的东西你看到没有」可自证；交接文档固定写「改了 `src/` 必须重启」；用户报「没变化」时先问一个**上一轮改动的可见结果**是否生效——能一步区分缓存与改错位置；定时器类配置走 `PUT /api/admin/settings`（内部会重建定时器，无需重启）。
- **适用场景**：无构建的原生前端 + 常驻 Node 服务；一切「改了但没生效」的排查。

### P4 配置系统的四个语义陷阱
- **现象**：只保存 ERP 卡片却被拦「启用快递100 前，请填写授权码 customer」，整个配置页写不进去；填错的凭据永远撤不掉；把自动同步改成 30 分钟，`PUT` 返回 `ok:true, saved:0` **静默不生效**。
- **根因**：① 组合校验跑在本次提交的**局部补丁**上，而敏感字段留空表示「保持原值」，已加密入库的值在补丁里是空串 → 被判成未填；② 敏感字段只有「留空 = 保持」一种语义，没有「显式清空」；③ 字段 `default` 对已有库的存量值无效（默认值只在「从未保存过这一项」时生效），且写入键名必须是完整 key `tracking.pollIntervalMinutes`（顶层的便捷回显字段不参与写入）。
- **规避**：组合校验在「已保存 + 本次补丁」**合并后的生效配置**上做；敏感字段支持 `null = 清空` / `'' = 保持`；改默认值的同时改存量值并回读核对；审计摘要对敏感字段固定写「敏感字段已更新（不记录明文）」并清理历史明文（含 customer 明文记录 1 → 0）。
- **适用场景**：后台可视化配置 + 加密凭据 + 审计的系统。

### P5 生产部署与常驻的硬约束
- **现象**：宝塔默认 Node 16/18/20 报 `Cannot find module 'node:sqlite'`；只搬库导致「接口配置」页全部解不开；项目目录设错后「登录成功但一条数据都没有」；内网部署时下拉箭头/复选框对勾/弹窗关闭图标全部 404；launchd 报 `Bootstrap failed: 5` 且与手动实例抢端口导致无限重启。
- **根因**：项目用内置 `node:sqlite` 需 **Node ≥ 22.5.0**；凭据 AES 加密入库，`data/.settings.key` 是唯一解密凭据；`src/config.mjs` 用 `process.cwd()` 解析 `.env` 与 `data/`（目录错会静默新建空库）；Shoelace 的 basePath 找不到 script 标签就回落到官方 CDN；KeepAlive 与 nohup 实例不能共存。
- **规避**：三条硬约束写进部署文档并作为排障第一顺位（Node 版本 / `.settings.key` 必须与库一起搬 / 工作目录必须是项目根）；迁库后账号仍是 `demo/****`（`.env` 只在 users 表为空时生效）→ 上线第一件事改口令；数据包用 `VACUUM INTO` 做一致性快照并校验 `integrity_check`；组件资源根路径用 `setBasePath` + `data-shoelace` 双保险钉死，E2E 断言**外部域名请求为 0**；注册 launchd 前先停掉手动实例。
- **适用场景**：内网/私有化部署、无第三方依赖的 Node 项目、Web Components 自托管。

## 五、测试与验收

### T1 vm 单测与真实浏览器测试的分工
- **现象**：drawer 测试桩的 `querySelector` 永远返回新建的空 div，新断言取不到真实文本；换组件后真正可聚焦的节点跑进了 shadow DOM。
- **根因**：vm + DOM stub 只能验证渲染字符串与接线，测不到真实事件、焦点、几何与溢出。
- **规避**：纯函数、渲染结构、URL/参数拼装用 vm 单测（快、无需浏览器）；shadow DOM 事件、`FormData` 取值、焦点陷阱、背景滚动锁、键盘可达性、控件等高、窄屏溢出与折行必须真实浏览器（`npm run test:browser` 从 68 项增至 **108 项**）；给 stub 派发事件时补 `target`（真实 DOM 事件必有 target）。
- **适用场景**：原生 JS + Web Components 的前端测试策略。

### T2 测试的三种假信号：假绿、假红、脚本自身缺陷
- **现象**：mock 数据永远满足渲染条件，而真实库 180 条全是 `delivery` 时两个区块从未渲染；断言钉死 43px 而实际 42px、账户 40px 而实际 41px；固定 `waitForTimeout` 抢跑（宽度有 200ms 过渡）；限流用例 gap 112~128ms、5ms 容差随机变红；两个端口并发跑共用 `data/.e2e.sqlite` → `attempt to write a readonly database` 假失败；创建账号弹窗故意保留，遮住删除弹窗按钮导致脚本崩。
- **根因**：fixture 固化了缺陷设计（旧断言写「销售发货单不显示采购信息」）；像素与计时断言对设计/调度漂移敏感；E2E 脚本自身有状态（临时库路径、上一步没关的弹窗）。
- **规避**：E2E 临时库按端口隔离；等待条件成立用 `waitForFunction` 而不是固定 sleep；断言改「等高 + 合理区间」；计时容差放宽到 20ms（「完全没限流」仍能被抓到）；fixture 取自真实库形状；改缺陷时同步改掉固化缺陷的旧断言。
- **适用场景**：长期维护的测试套件；含真实浏览器的 E2E。

### T3 排查先取证：不猜位置、不猜样式、不猜配置
- **现象**：必填星号换行按「推测的位置」精准修了两轮都没修好，第三轮改成不依赖位置假设的 `flex-wrap: nowrap` 才生效；`.detail-title` 只有 `align-items: center` 而没有 `display: flex`（对块级元素完全无效），674px 单列 grid 里两个小元素分两行；诊断脚本把库里的字符串 `"true"` 直接喂给配置构造函数，因 `"true" !== true` 落回演示分支，得到「0 条轨迹」的假象。
- **根因**：读源码看不出真实计算样式与几何；诊断路径绕过了负责类型转换的那一层。
- **规避**：用 Playwright 读真实计算样式与 `getBoundingClientRect`，**先量后改**；用同页对照组（把抽屉 `--size` 压回 760px、注入旧样式备份）区分「本次引入」与「既有」；取配置一律走 `readSettings` / `readEffectiveSettings`；第一时间索取截图；批量替换写成带选择器前缀或负向断言（`(?<![-\w])font-size:`）的精确匹配，避免 `.mono` 这类同名声明被误伤。
- **适用场景**：UI 修复与配置驱动排查；无浏览器可视化环境的远程协作。

### T4 同一工作区多会话并发编辑的纪律
- **现象**：反复出现 `file changed since it was read`；`app.js` 在一次阅读期间从 1363 → 1412 → 1430 行；测试总数 199 → 214 → 231 → 262 → 274 持续漂移；别人的中间态（`ref_msku.market` 缺列、`app.js` 语法未补完）让自己这边出现「假红灯」。
- **根因**：多会话/多人同时改同一批文件，整文件写入会吃掉对方改动；瞬时中间态被当成了结论。
- **规避**：只做**局部 edit、绝不整文件 write**（`old_string` 不匹配即失败，等于免费的冲突检测）；每次编辑前重新 read 并看 mtime；改完立刻 `grep` + `node --check` + `npm test` 复核自己的改动仍在；端到端只断言本功能负责的契约（「不因权限被拒」而不是「一定 200」）；看到别人的半成品先复核当前文件内容再下结论，不擅自替对方改。
- **适用场景**：AI 多会话并行 / 多人共享工作区；非 git 仓库的工作流。

## 最高频的三个坑

**排序依据**：① 在四份文档中的出现次数（`grep -o` 计数：断言 71、覆盖 61、重启 49、口径 43、缓存 14、静默 12）；② 跨交付轮次的复现度（文档共 15 个「本次交付/本次追加」小节、6 个「踩过的坑」小节，按根因归属统计：UI/样式类修复约 13 轮但分散在十余个不同根因上，而下面三个坑是**同一根因跨轮次反复出现**）；③ 影响面（是否造成数据作废、服务不可用或用户可见的错数字）。

1. **改了却没生效**（C1、P3、P4）——出现面最广：「重启」49 次、「缓存」14 次，几乎每次交付都要提醒「改了 `src/` 必须重启」；形态包括后端未重启、前端被缓存且无法自证、CSS 被更靠后的块覆盖、字段默认值改了但存量值还在。影响面是持续白跑排查与「新功能点了没反应」。
2. **同一个概念在两处口径/语义不同**（D1、D2、D4、P4）——「口径」43 次；代表案例：卡片 15 vs 列表 173、关联键 0/116 与 0/539 却 7728/7728、`order_items.erp_order_id` 存业务 `erp_id` 被当成自增主键、跨模块字段名 `trackingNoStrategy`/`strategy` 不一致。影响面最隐蔽：不报错，只显示空白或错数字。
3. **失败被静默吞掉**（P2、S4、S5、D2、D6）——「静默」12 次，但影响面最大：手填令牌短路让定时同步每 20 分钟失败一轮共 **698 轮**、数据冻结 2 天且日志无痕；`catch {}` 让每轮固定 **41 条**失败无法诊断；HTTP 错误体被丢弃让用户反复猜；模型层的失效最终都以「页面上看起来没数据」的形式暴露。

# 排查「改了没生效」

**什么时候用**：用户说「没有变化 / 没生效 / 还是旧的 / 显示不对」，或你自己刷新后没看到预期改动。
**做完手上有什么**：一句分层结论（问题在**生效层** / **命中层** / **分支层**哪一层）+ 该层的命令输出或量值；若已修复，附改前改后各一张截图。

分层：**生效层**＝服务端有没有把新文件发出去（缓存、未重启）；**命中层**＝CSS/组件规则有没有作用到这个节点（被覆盖、选择器不匹配、插槽与高度）；**分支层**＝作用到了但不是用户那条分支（角色、媒体查询、局部刷新遗漏）。

**前置**：第 6–8 步用 `.probe/verify-ui-change.mjs`（脚本见 `playbooks/改前端并自证生效.md` 第 3 步），跑在 3211 的临时实例上（起法见同文档第 2 步，不要用生产 3000）；示例里的 `demo/demo123` 只在空库（users 表为空）时有效，用副本库时换成库内真实账号。

## 步骤

1. **固定现场，先不改代码**
   - 命令 / 做法（项目根，下同）：
     ```bash
     stat -f '%Sm %N' public/app.js public/styles.css public/sidebar.css src/*.mjs
     lsof -nP -iTCP:3000 -sTCP:LISTEN
     ```
   - 判据：记下前端三件套与相关 `src/` 文件的 mtime、3000 端口 PID；未记录前不动代码（改了会污染现场）。

2. **先问用户一个能分层的二选一问题**
   - 命令 / 做法：问「上一轮改动的**可见结果**是否生效」（不是问「你看的是新版吗」）。
   - 判据：拿到「是 / 否」。答「否」→ 走第 3 步（生效层）；答「是」→ 走第 5 步（命中层）（案例 P3：一步区分缓存与改错位置）。

3. **生效层 · 资源与缓存**
   - 命令 / 做法：
     ```bash
     curl -s http://127.0.0.1:3000/ | grep -oE '(app|styles|sidebar)\.(js|css)\?v=[0-9]+'
     curl -s http://127.0.0.1:3000/ | grep -oE 'app\.js\?v=[0-9]+'     # 再打一次，看是否稳定
     node -e "const f=require('fs');const m=['app.js','styles.css','sidebar.css'].map(n=>f.statSync('public/'+n).mtimeMs);console.log('文件版本号 '+Math.round(Math.max(...m)))"
     ```
     用户走的是内网 IP / 反向代理时，把 URL 换成他实际访问的地址（案例 P5）。
   - 判据（`src/server.mjs` 的 `assetVersion()` 只有两个返回值，因此只有三种情况）：
     - 两次 curl 版本号**不同** → 走了 `Date.now()` 兜底分支，说明运行中的进程不是当前代码（旧的常驻进程）→ 直接走第 4 步重启；
     - 版本号稳定但**不等于**本地文件版本号 → 进程读到的 `public/` 不是这一份（启动目录不对）→ 按案例 P5 核对工作目录；
     - 两者**相等** → 生效层没问题，问题在浏览器或中间层缓存（硬刷新，或核对响应头 `Cache-Control`），转第 5 步。

4. **生效层 · 服务未重启**
   - 命令 / 做法：
     ```bash
     ps -o pid,lstart,command -p $(lsof -ti tcp:3000 | head -1)
     npm start          # 单独终端；开发期可用 npm run dev（--watch，自动重启）
     ```
   - 判据：进程启动时间晚于 `src/` 最后修改时间，并把启动日志时间戳贴进交付说明。规则：`public/` 下的静态资源每次请求重读、不需要重启；`src/` 改动必须重启（案例 P3、P5）。

5. **命中层 · 规则被覆盖**
   - 命令 / 做法：先静态比对声明次序，再读浏览器最终值。
     ```bash
     grep -rnE "backdrop-filter|--sidebar-w|你的属性名" public/*.css
     ```
     判据一（静态）：本次改动所在行必须晚于所有同属性竞争声明。存在 `#id`、`.a.b`、`!important` 或媒体查询时行号法不成立，必须读最终值。
   - 判据二（动态）：用 `playbooks/改前端并自证生效.md` 第 3 步的探针脚本，读该节点的 `getComputedStyle().<属性>`；值不等于你写的常量，就是被更靠后的块覆盖（案例 C1：4 段框架规则共 408 行，宽度 232px / 220px / 204px 三套并存）。
   - 修复方式：删掉失效块，把尺寸收回到一个变量，而不是继续在后面追加。

6. **命中层 · 选择器不匹配**
   - 命令 / 做法：
     ```bash
     grep -rn "你的新类名" public/*.css public/*.js
     PROBE_BASE=http://127.0.0.1:3211 PROBE_ADMIN_USER=demo PROBE_ADMIN_PASS=demo123 \
       PROBE_SELECTORS='.你的新类名' node .probe/verify-ui-change.mjs
     ```
     组件内部节点必须带 `>>>` 查进 shadow DOM：`PROBE_SELECTORS='sl-select[multiple] >>> .select__tags'`。
   - 判据：输出里 `missing: true` → 真实 DOM 里没有这个节点（模板没渲染 / 类名写错）；宿主存在但 shadow 内查不到 → 结构与插槽假设错了（案例 C3、C5、T1）。

7. **命中层 · 组件插槽与高度**
   - 命令 / 做法：
     ```bash
     grep -rn -- "--sl-input-height-(small|medium|large)" public/*.css
     grep -rn "part(base)" public/*.css            # 命中处不得有 padding
     PROBE_BASE=http://127.0.0.1:3211 PROBE_ADMIN_USER=<账号> PROBE_ADMIN_PASS=<口令> \
       PROBE_SELECTORS='.account-button,.filter-panel sl-select[multiple]' node .probe/verify-ui-change.mjs
     ```
   - 判据：控件高度等于该档位常量（账户 40 / 筛选 40 / 表格按钮 30）——实测过 79px（内容堆在默认插槽）、54px（`::part(base)` padding 叠加）、145px（多选标签换行），出现这三种数就是命中这三个根因（案例 C3、C6）。

8. **分支层 · 角色 / 媒体查询 / 局部刷新遗漏**
   - 命令 / 做法：
     ```bash
     PROBE_BASE=http://127.0.0.1:3211 PROBE_VIEWPORTS=1920,1440,1180,1100,1024,900,760,560,380,375 \
     PROBE_ADMIN_USER=<管理员> PROBE_ADMIN_PASS=<口令> \
     PROBE_MEMBER_USER=<普通用户> PROBE_MEMBER_PASS=<口令> \
     node .probe/verify-ui-change.mjs
     grep -n "@media" public/sidebar.css public/styles.css | grep -oE "max-width: [0-9]+px" | sort -u
     grep -n "layoutCleanup\|shipmentRequestSeq\|sync-freshness" public/app.js
     ```
   - 判据：每个 `@media` 断点（本项目实测 380 / 560 / 760 / 900 / 1100 / 1180px）都要有断点**两侧**的视口被跑到，且数值都在预期内；只验管理员 = 未完成（案例 C2：只有普通用户分支塌成 64px）。改动新出现的区块必须在局部刷新函数里有固定 id，否则整页刷新才更新 = 遗漏（案例 C9）。

9. **收口：把根因写成断言，再复跑全量**
   - 命令 / 做法：
     ```bash
     npm test
     npm run test:browser          # 端口冲突时 E2E_PORT=3212 npm run test:browser
     ```
   - 判据：新增一条能复现该根因的断言（等高 + 合理区间，不要钉死单个像素）；`npm test` 274/274、`npm run test:browser` 108/108（以最后一次记录为准）。没加断言的修复视为没修完。

## 常见坑（来自案例集）

| 坑 | 表现 | 规避 |
| --- | --- | --- |
| 前端被缓存且无法自证（案例 P3） | 用户「刷新了没变化」，你无法证明他加载的是哪一版 | 服务端把 `/app.js`、`/styles.css`、`/sidebar.css` 改写成 `?v=<mtime>`，并显示界面版本 |
| 改了 `src/` 没重启（案例 P3） | 新列、新排序「点了没反应」 | 交付说明里贴启动日志时间戳；开发期用 `npm run dev` |
| 只验一个角色（案例 C2） | 管理员正常，普通用户顶栏塌 64px | 多角色矩阵当作必跑项，不是可选项 |
| fixed 元素基准被祖先改掉（案例 C2） | 宽度塌缩、`left` 算出来的位置全错 | 查祖先的 `filter` / `transform` / `backdrop-filter` / `contain` |
| 固定 sleep 抢跑（案例 T2） | 宽度有 200ms 过渡，断言随机假红 | 改 `waitForFunction` 等条件成立，不写死 `waitForTimeout` |
| 断言钉死像素（案例 T2） | 设计微调 43px→42px 就让用例假红 | 断言「等高 + 合理区间」，容差按实测放宽到 20ms / 1px |

## 收尾自检
- [ ] 结论明确落到某一层，并附该层的命令输出或量值（不是「可能是缓存」）
- [ ] 修复动作是删失效块 / 改唯一出处，不是再叠一层覆盖
- [ ] 多角色 × 每个媒体查询断点都跑过，数值在预期内
- [ ] 新增了一条能复现该根因的断言，`npm test` 与 `npm run test:browser` 全绿
- [ ] 交付里含改前改后截图 + 关键量值，并说明「改了 `src/` 已重启（附时间戳）」

# 接入外部接口

**什么时候用**：要接一个新的外部 API（新数据源、新查询路径、新状态接口），或给已有同步器加一个接口；用户说「对接 XX 接口」「把 XX 数据拉进来」「这个接口字段对不上」时。
**做完手上有什么**：一份探测记录（真实返回格式 + 可用参数 + 无效参数 + 限流码）+ 一次小批量试跑的数字（processed / failed / filtered / 用时）+ 一次连跑两遍的行数对比 + 一条故意失败的可读错误记录。

## 步骤

1. **建副本库与临时端口，先不碰生产**
   - 命令：
     ```bash
     cp data/logistics.sqlite data/.probe-api.sqlite
     cp data/.settings.key data/.probe-api.key
     DATABASE_PATH=./data/.probe-api.sqlite SECRET_KEY_PATH=./data/.probe-api.key PORT=3211 node src/server.mjs
     ```
   - 判据：另开一个终端 `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3211/api/health` 输出 `200`；生产 3000 端口进程没有被重启。`.settings.key` 必须与库一起复制，否则加密凭据解不开（案例 P5）。

2. **探测字段与限流（只读，不写业务数据）**
   - 命令：
     ```bash
     DATABASE_PATH=./data/.probe-api.sqlite SECRET_KEY_PATH=./data/.probe-api.key node tools/probe-erp.mjs delivery-page
     ```
   - 判据：写下四件事，缺一件不算完成——① 返回格式（JSON / XML，是否随请求参数变化）；② 限流码与文案（实测 `90008` / HTTP `509` /「接口调用次数已超过限制次数」）；③ **有效**的服务端筛选参数；④ **实测无效**的参数，记进「已实测无效」清单以后不再试。字段必须看原文：`trackings` 实测返回「公司名 + 单号」混串，不能假设结构化字段就是干净值（案例 D3）。

3. **小批量试跑，量出调用量与时长**
   - 命令：
     ```bash
     DATABASE_PATH=./data/.probe-api.sqlite SECRET_KEY_PATH=./data/.probe-api.key node .probe/run-sync.mjs
     ```
   - 判据：拿到具体数字（`processedCount` / `failedCount` / `filteredCount` / 用时秒数），而不是「看起来跑通了」；由「列表页数 + 逐单明细次数」估算一轮接口调用次数并对照预期（案例 S2 下推后：列表 4 次、总量 176 条）；`failedCount` 必须为 0，若不为 0 必须能从 `failures` 样本读出原因。

4. **落库与幂等：同一份数据连跑两遍不增行**
   - 做法：把步骤 3 的命令再执行一遍，然后用行键核对。
   - 命令：
     ```bash
     sqlite3 data/.probe-api.sqlite "SELECT COUNT(*) - COUNT(DISTINCT erp_order_id || '|' || line_key) FROM order_items;"
     sqlite3 data/.probe-api.sqlite "SELECT (SELECT COUNT(*) FROM shipments), (SELECT COUNT(*) FROM erp_orders), (SELECT COUNT(*) FROM order_items);"
     ```
   - 判据：两遍跑完三次计数完全一致；唯一性差值为 0；明细行主键是**行级 ID**（上游单据级 `fid` 同一交货单 6 行全是 `54331`，用了就会撞 `UNIQUE(erp_order_id, line_key)`，案例 D2）。

5. **失败必须可观测（故意失败一次）**
   - 做法：把凭据改错，或在副本里塞一个不存在的单号，跑一轮。
   - 命令：
     ```bash
     sqlite3 data/.probe-api.sqlite "SELECT status, processed_count, failed_count, error_summary FROM sync_runs ORDER BY id DESC LIMIT 3;"
     ```
   - 判据：`error_summary` 能直接读出原因并含上游 `code` / `messages`（不是「HTTP 401」这种丢弃响应体的结论，案例 S4）；确认接口失败**没有覆盖**上一次有效状态（案例 S6）。

6. **放开量级：限速、串行、互斥、冷却齐备**
   - 判据（逐条核对，缺一不可）：
     - 同一上游两次调用间隔 ≥ `minIntervalMs`（默认 600ms，实测上游 2 次/秒）（案例 S1）；
     - 同一上游批量调用无 `Promise.all`，改串行（案例 S1）；
     - 并发触发第二次同步立即返回 `skipped`，不排队（案例 S3）；
     - 失败单有最小重查窗口（实测 6 小时冷却）（案例 S5）；
     - 会丢弃的数据在服务端就过滤掉，不调用明细接口（案例 S2）。
   - 命令（验证互斥：第一条放后台，第二条立刻发，登录 cookie 见下方说明）：
     ```bash
     curl -s -X POST http://127.0.0.1:3211/api/admin/sync -H 'Content-Type: application/json' \
       -b /tmp/probe-api.cookies -d '{}' > /tmp/sync-first.json &
     sleep 2
     curl -s -X POST http://127.0.0.1:3211/api/admin/sync -H 'Content-Type: application/json' \
       -b /tmp/probe-api.cookies -d '{}' | head -c 300
     ```
     判据：第二条响应里出现 `skipped`（不排队、不并发跑第二轮）；如果第二条返回的是完整同步结果，说明第一条还没进锁，把 `sleep 2` 加到 `sleep 5` 再试。

7. **切生产：先清掉旧条件数据，再按新条件重拉**
   - 命令：
     ```bash
     node tools/reset-business-data.mjs          # dry-run：看清将要清空多少条
     node tools/reset-business-data.mjs --apply  # 内部先 VACUUM INTO 备份，再单事务清空
     ```
   - 判据：dry-run 的条数与预期一致；`--apply` 后 `shipments` / `erp_orders` / `order_items` / `tracking_events` 为 0，而 `settings` / `users` / `ref_*` / `sync_runs` 行数不变。**注意**：服务启动时若发现物流单为空会自动触发一次全量同步，先确认上游配额充足再重启。完整演练流程见 `改数据逻辑并在副本验证.md`。

> 需要调后台接口时先拿会话 cookie（`demo` / `demo123` 仅演示环境）：
> ```bash
> curl -s -X POST http://127.0.0.1:3211/api/auth/login -H 'Content-Type: application/json' \
>   -d '{"username":"demo","password":"demo123"}' -c /tmp/probe-api.cookies
> curl -s -X POST http://127.0.0.1:3211/api/admin/settings/test -H 'Content-Type: application/json' \
>   -b /tmp/probe-api.cookies -d '{"target":"erp","values":{}}'
> ```
> `target` 可取 `erp` / `lotno` / `reference` / `tracking` / `identify`；`identify` 与 `tracking` 可额外带 `trackingNo`、`courierCode`。

## 常见坑（来自案例集）

| 坑 | 表现 | 规避 |
| --- | --- | --- |
| 限流当总量（案例 S1） | 判成「当日额度用尽、等次日恢复」，方向整体跑偏 | 实测 2 次/秒；全局限速 600ms + 指数退避 + 并发改串行 |
| 为要丢弃的数据付调用成本（案例 S2） | 为 176 条拉 2500 条，预计 ~75 分钟 | 先探测服务端筛选（`transportList` / `statusList`）再拉明细 |
| 结构化字段原样落库（案例 D3） | 224 条 `S66565296289顺心捷达`，快递100 一律 400 | 落库前按形态正则校验，判据是「有没有非单号字符」不是长度 |
| 只认一种返回格式（案例 S6） | 「错误码 无：ok」——成功 XML 被报成错误 | 先 `text()` 再判状态；JSON/XML 与 `{success,error_msg,track_data}` 都解析 |
| 状态只看顶层码（案例 S6） | 正常派件被标成运输异常 | 固定优先级：最新节点 status → ischeck → state → 正则 |
| 手填令牌短路（案例 S4） | 每 20.0 分钟失败一轮，累计 698 轮 | 被拒后永久回退 AppId+AppKey 自动换取；重试覆盖两条路径 |
| 错误体被丢弃（案例 S4） | 只有「HTTP 401」，用户反复猜 | 保留上游 `code` / `messages` 并透出到界面与日志 |
| 已试过的无效参数反复试（案例 S2） | 反复传 `transportName` / `status` 等，白耗调用 | 维护「已实测无效」清单，写进接入文档 |

## 收尾自检
- [ ] 探测记录里有限流码、有效参数、无效参数三类清单
- [ ] 小批量试跑有具体数字；`failedCount` 为 0，或有可读原因样本
- [ ] 幂等成立：连跑两遍行数不变、行键唯一性差值为 0
- [ ] 故意失败一次后能从 `sync_runs.error_summary` 直接读出原因
- [ ] 限速 + 串行 + 互斥 + 冷却 + 筛选下推五项齐备
- [ ] 切生产前已 dry-run，且 `VACUUM INTO` 备份已生成、`integrity_check` = ok
- [ ] 临时服务已停（`lsof -ti:3211 | xargs kill`），副本库与副本密钥已删

# 改数据逻辑并在副本验证

**什么时候用**：要改 SQL、迁移表结构、清库、重拉、批量补数据、清洗历史脏值时；需要以另一个角色（普通用户）登录验证、但又不能动生产账号时。用户说「把数据清一下重拉」「这条脏数据批量修掉」「用普通用户视角看看」时。
**做完手上有什么**：一份一致性备份（`VACUUM INTO` + `integrity_check` 通过）+ 副本上的 dry-run 数字 + 副本 `--apply` 后的前后行数对比 + 一次真实入口回归结果 + 一条「没有在生产库试密码」的证据。

## 步骤

1. **先冻住现场：一致性备份，不要用 `cp`**
   - 命令：
     ```bash
     STAMP=$(date +%Y%m%d%H%M)
     sqlite3 -cmd ".timeout 15000" data/logistics.sqlite "VACUUM INTO 'data/logistics.bak-$STAMP.sqlite';"
     sqlite3 "data/logistics.bak-$STAMP.sqlite" "PRAGMA integrity_check;"
     ```
   - 判据：备份文件存在，且 `integrity_check` 输出 `ok`。服务可能正在读写，直接 `cp` 会拿到不一致的快照（案例 P5 用 `VACUUM INTO` 做一致性快照）。

2. **建副本库 + 独立端口 + 独立密钥**
   - 命令：
     ```bash
     cp data/logistics.sqlite data/.probe-fix.sqlite
     cp data/.settings.key data/.probe-fix.key
     DATABASE_PATH=./data/.probe-fix.sqlite SECRET_KEY_PATH=./data/.probe-fix.key PORT=3211 node src/server.mjs
     ```
   - 判据：另开终端 `curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3211/api/health` 输出 `200`；生产 3000 端口仍在正常服务。密钥必须与库一起搬，否则「接口配置」页全部解不开（案例 P5）。

3. **在副本上 dry-run，先看清会影响什么**
   - 命令（清库预演）：
     ```bash
     DATABASE_PATH=./data/.probe-fix.sqlite node tools/reset-business-data.mjs
     ```
   - 命令（历史脏值清洗预演）：
     ```bash
     DATABASE_PATH=./data/.probe-fix.sqlite node tools/repair-tracking-no.mjs
     ```
   - 判据：输出「将要清空 / 修改的条数」以及会走的分类（清洗 / 合并 / 降级）；跑完再查一次 `COUNT(*)` 与跑前一致——无 `--apply` 必须一行都不写。

4. **在副本上执行，并逐表核对前后行数**
   - 命令：
     ```bash
     DATABASE_PATH=./data/.probe-fix.sqlite node tools/reset-business-data.mjs --apply
     sqlite3 data/.probe-fix.sqlite "SELECT (SELECT COUNT(*) FROM shipments), (SELECT COUNT(*) FROM erp_orders), (SELECT COUNT(*) FROM order_items), (SELECT COUNT(*) FROM tracking_events);"
     ```
   - 判据：该清的表为 0，`settings` / `users` / `ref_*` / `sync_runs` 行数不变；有外键级联时关联零丢失（案例 D3 迁移的验收数字：清洗 **129 条** + 合并 **10 组**，`erp_orders` **2524 条**关联零丢失）。

5. **用真实入口在副本上回归**
   - 命令：
     ```bash
     PROBE_BASE=http://127.0.0.1:3211 node .probe/verify-stat-card-filter.mjs
     npm test
     E2E_PORT=3212 npm run test:browser
     ```
   - 判据：口径断言全绿（卡片数字 = 对应筛选 `total`；未签收 + 待填写 + 已签收 = 全部）；`npm test` 与浏览器测试全过。E2E 临时库按端口隔离（`.e2e-<PORT>.sqlite`），不要多个端口共用同一个临时库。

6. **要换角色登录，就在副本里改哈希，绝不在生产库试密码**
   - 做法：把目标账号的 `password_hash` 复制成已知可用账号的值，再在副本服务（3211）上登录。
     ```bash
     node -e "const { DatabaseSync } = require('node:sqlite'); const db = new DatabaseSync('data/.probe-fix.sqlite'); db.exec(\"UPDATE users SET password_hash = (SELECT password_hash FROM users WHERE username = 'demo') WHERE username = 'admin'\");"
     ```
   - 判据：副本上能以该角色正常进入；生产库 `auth_events` 没有新增失败记录：
     ```bash
     sqlite3 data/logistics.sqlite "SELECT username, COUNT(*) FROM auth_events WHERE success = 0 GROUP BY username;"
     ```
   - 真实事故：曾在**生产库**上用 `admin/demo123` 试错 3 次，触发「该账号 15 分钟内已失败 3 次」锁定（约 11:08 起、11:23 后自动解除）。正确做法就是本步骤（出处：`docs/侧边栏重构-交接文档.md`「踩过的坑」第 3 条）。

7. **对生产执行：先修缺陷，再跑补数**
   - 命令：
     ```bash
     node tools/reset-business-data.mjs          # dry-run，数字必须与副本演练一致
     node tools/reset-business-data.mjs --apply  # 内部先 VACUUM INTO 备份，再单事务执行
     ```
   - 判据：生产 dry-run 的条数与副本演练一致；脚本内部已留 `VACUUM INTO` 备份；全程单事务、出错自动 `ROLLBACK`。若 dry-run 显示会走删除/合并分支，**先修该缺陷再执行**（案例 D5）；删除前必须先把子行改指目标父行。
   - 提醒：服务启动时若发现物流单为空会自动触发一次全量同步，执行前确认上游配额充足（案例 P2）。

8. **收尾：停临时服务、删副本制品**
   - 命令：
     ```bash
     lsof -ti:3211 | xargs kill
     rm -f data/.probe-fix.sqlite data/.probe-fix.key
     ```
   - 判据：`lsof -ti:3211` 无输出；生产库仍是唯一在跑的实例；`git status`（若用 git）里没有副本制品残留。

## 常见坑（来自案例集）

| 坑 | 表现 | 规避 |
| --- | --- | --- |
| 用 `cp` 当备份（案例 P5） | 服务正在写，快照不一致，回滚也回不去 | `VACUUM INTO` + `PRAGMA integrity_check` = ok |
| 只搬库不搬密钥（案例 P5） | 迁库后「接口配置」页全部解不开 | `.settings.key` 必须与库一起复制 |
| 先删父行（案例 D5） | 占位单上的全部单据被级联删掉，调用方只重建一条 | 事务内先 `UPDATE` 子行外键，再 `DELETE` 父行 |
| 在生产库试密码（`docs/侧边栏重构-交接文档.md`） | `admin` 账号 15 分钟锁定 | 副本库改 `password_hash`，临时端口登录 |
| 没 dry-run 直接改生产（案例 D5） | 批量删除无法预判、没有回滚点 | 脚本默认 dry-run，`--apply` 才写库，且先备份 |
| 清库后直接重启（案例 P2） | 空库触发启动全量同步，白烧上游配额 | 先确认配额；启动引导同步必须包 try/catch、照常 `listen` |
| 多端口共用 E2E 临时库（案例 T2） | `attempt to write a readonly database` 假失败 | 临时库按端口隔离（`.e2e-<PORT>.sqlite`） |

## 收尾自检
- [ ] 备份存在且 `integrity_check` = ok，备份路径已记录
- [ ] 副本库与副本密钥都在 `data/.probe-*`，生产库未被本流程直接改过
- [ ] 生产执行的 dry-run 数字与副本演练一致
- [ ] 有外键级联的表已核对子行零丢失（前后 `COUNT(*)` 对比）
- [ ] `npm test` 与 `PROBE_BASE` 口径断言在这次改动后全过
- [ ] 换角色验证走的是副本，生产 `auth_events` 无新增失败
- [ ] 临时端口已 kill，副本库/密钥/临时 cookie 已删

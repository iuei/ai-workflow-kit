# 外部接口与同步规则

> 来源：工程案例集 S1–S6（并以 P2、D2 的静默失败作为同一根因的旁证）；每条都对应一次真实事故，后果写在条目里。
> 这组事故的共同形态是「不报错、只沉默」：定时器 698 轮全失败但日志只有一行、每轮 41 条入库失败只累加计数。复盘里「服务中断 / 反复启动」73 条是最高频摩擦，见 `../appendix/session-report.md`。
> 用法：可直接追加到项目 AGENTS.md，或作为接入 / 维护外部接口时的自查清单。
> 排序：按致命程度——先「失败不可见」（R1–R2），再「调用方式错」（R3–R6），再「解析与容错」（R7–R9），最后一条是测试纪律（R10）。
> 命令前置条件：需要凭据的探针与同步脚本都在**副本库**上跑并显式传 `DATABASE_PATH` / `SECRET_KEY_PATH`；`data/logistics.sqlite` 指生产库（只读查询）。

## 一、必须

### R1 失败不得静默：catch 留样本、错误体必透出
- **规则**：禁止空 `catch {}`；每个 catch 至少要记录可读原因样本（随结果返回，最多 10 条）。非 2xx 响应必须先 `await response.text()` 再判状态，并把上游 `code` / `messages` 放进错误信息。每个同步阶段结束后必须显式检查 `result.failures` 并落日志。
- **为什么**：`catch {}` 只累加计数，让「每轮固定几十条失败」变成无法诊断的问题（案例 D2、P2）；`erpFetch` 在 `!response.ok` 时直接抛「HTTP 401」并丢弃响应体，用户只能反复猜（案例 S4）。
- **怎么检查**：
  - `grep -rn "catch {}\|catch {$" src/` 不得命中；`grep -n "failures" src/sync.mjs` 必须能看到失败样本被收集并随返回值 / 进度返回。
  - `grep -n "response.ok" -A5 src/providers.mjs`，其后的错误分支必须出现 `text()`（先取正文再判状态）。
  - 故意把令牌改成错的，跑一轮后查：
    `sqlite3 data/logistics.sqlite "SELECT status, processed_count, failed_count, error_summary FROM sync_runs ORDER BY id DESC LIMIT 1;"`
    `error_summary` 必须写明原因，而不是「未记录失败原因」。
  - 阶段级容错后必须显式消费 `result.failures`，否则「ERP 鉴权失效」这类故障只剩 `sync_runs` 表里一行、日志彻底静默（案例 P2）。
- **违反后果**：定时器每 20.0 分钟精确跑一轮、累计 **698 轮**全部失败，数据冻结 **2 天**，日志里只有一行 `sync_runs` 失败；另有 **43.8 小时**完全无同步记录（`setInterval` 不补跑错过的轮次）（案例 S4、P2）；`catch {}` 让每轮固定 **41 条**失败无法诊断（案例 D2）。

### R2 令牌失效必须自愈，重试判定两条路径共用
- **规则**：禁止「有令牌就直接 return」的短路；手填令牌被上游拒绝后必须**永久回退** AppId+AppKey 自动换取；重试判定必须同时覆盖「非 2xx」与「200 + 业务码」两条路径，并按真实响应形态写测试（实测形态：HTTP 401 + code 40005 +「token已失效」）。
- **为什么**：`ensureAccessToken` 首行 `if (accessToken) return` 让手填令牌永久短路自动换取，24 小时过期后每轮 401；而重试条件写成 `!accessToken`，连兜底重试也不生效（案例 S4）。
- **怎么检查**：
  - `grep -n "ensureAccessToken" -A6 src/providers.mjs`，函数开头不得是无条件返回已有令牌。
  - `grep -rn "accessToken" src/providers.mjs`，重试条件不得依赖令牌是否存在。
  - 换取令牌路径必须归一化：基地址已含 `/api/open` 时路径不能再拼 `/api/open`，否则拼成 `.../api/open/api/open/api_token` 被网关拒成 401；`grep -n "normalizeTokenPath" src/config.mjs` 确认历史配置会被就地纠正。
  - 回归用例：把令牌设成失效值跑一轮，要求**数据仍能更新**（证明自动换取生效），而不是只看接口返回 200。
- **违反后果**：累计 **698 轮**每轮 401、数据冻结 2 天；且第一次修复线上**完全没触发**——重试只写在「HTTP 200 + 业务码」分支、正则只匹配「鉴权失败」（案例 S4）。

### R3 限流按频率处理：全局限速 + 识别限流码 + 指数退避
- **规则**：所有对同一上游的调用必须经过统一排队，保证两次调用间隔 ≥ 官方最小间隔（实测 2 次/秒 → `minIntervalMs = 600ms`，留 20% 余量）；识别限流码（`90008` / HTTP `509` / 文案「超过限制次数」）后指数退避（`retryBaseMs = 1000`，1s→2s→4s）；同一上游的批量调用必须串行，禁止 `Promise.all`。
- **为什么**：真实规则是**每 1 秒 2 次**，`Promise.all` 并发直接绕过单次间隔限制；把它误判成「当日额度用尽、等次日恢复」会让排查方向整体跑偏（案例 S1）。
- **怎么检查**：
  - `grep -n "minIntervalMs" src/config.mjs src/providers.mjs`，确认默认 600 且发请求前统一 await 排队。
  - `grep -rn "Promise.all" src/providers.mjs`：同一上游的批量调用不得使用。
  - 用本地 mock 上游验证退避：前两次返回 509、第三次成功；一直 509 则重试耗尽后报错，且错误信息里能看出是限流（案例 S1 的验收方式）。
  - 限流码判定要同时看 HTTP 状态与业务码：`grep -n "90008" src/providers.mjs` 必须与 `status === 509` 并列，并额外匹配中文文案兜底。
- **违反后果**：由 `Promise.all` 并发打出的 5 个基础资料接口**必挂**，而 ERP 主同步（50 次分页）能成功——同一份代码一半能用一半不能用（案例 S1）。

### R4 调用量下推：先服务端筛选，再拉明细
- **规则**：写「分页拉取 → 本地过滤」之前，必须先探测上游可用筛选参数并下推到请求里；预判与落库必须共用同一份判据（`src/orderFilter.mjs`），本地过滤只作兜底；逐单调用的明细接口只对通过过滤的记录调用。
- **为什么**：筛选只在本地做（上游参数名未知），于是为 176 条有用数据拉 2500 条，明细又是逐单调用，不预判就要为 **2342 条**注定丢弃的记录白打两千多次接口（案例 S2）。
- **怎么检查**：
  - 打印一轮的 `filteredCount` 与 `processedCount`，`filteredCount` 不应接近总量（案例 S2 实测一轮 2500 条里只有 158 条能通过过滤）。
  - 确认请求里真的带上下推条件。实测**有效**：`transportList=['113']`、`statusList=['draft','picking','shipped','receiving']`（英文码）；实测**无效**：`transportName` / `transportCode` / `status` / `statusList=[1]`——已试过，不要再试，写进「已实测无效」清单。
  - 记录列表调用次数：下推后应为 **4 次**（2500 条按每页 50 计是 50 次）。
  - 预判与落库共用判据：`grep -rn "orderFilterReason" src/` 必须同时出现在同步流程与落库流程。
- **违反后果**：一轮预计 **~75 分钟**（下推后 ~6 分钟），并为 2342 条注定丢弃的记录白打两千多次接口（案例 S2）。

### R5 同步必须互斥，重复触发立即返回 skipped
- **规则**：所有同步入口（定时、手动、启动引导）必须共用一个 in-flight Promise 锁（`withLock`）；抢不到锁的调用立即返回 `{ skipped: true, reason }` 而不排队干等；前端拿到 `skipped` 不得假装「同步完成」。
- **为什么**：手动「立即同步」撞上定时同步（或重复点击）会真的并发跑两轮，两轮共用一个全局进度对象交替写入，还会重复消耗积加调用与快递100 额度、并发写同一个 SQLite（案例 S3）。
- **怎么检查**：
  - `grep -n "withLock\|inFlight" src/sync.mjs`，确认所有对外同步函数（含单路同步）都包在锁内。
  - 断言方式：mock 上游故意拖慢 150ms 制造并发窗口，要求「有且仅有一轮被跳过、上游只被调用一次」。
  - 现场核对：`sqlite3 data/logistics.sqlite "SELECT COUNT(*) FROM sync_runs WHERE finished_at IS NULL;"` 应 ≤1（历史上出现同时 2 条「运行中」记录，更早还有 3 条同时在跑）。
  - 前端分支：`grep -n "skipped" public/app.js`，命中处不得渲染成「同步完成」。
- **违反后果**：进度从「发货单：94 / 176 · 已用 43 秒」退回「20 / 176 · 已用 **43 秒**」——两次秒数完全相同是决定性线索；同时重复消耗额度、并发写库（案例 S3）。

### R6 配置错配必须在保存与测试连接时就拦截
- **规则**：域名、鉴权方式、路径三者必须成组校验：不匹配的组合必须在「保存配置」与「测试连接」两个入口就被拒（HTTP 400），不得等到同步时才报错。
- **为什么**：积加域名配非积加鉴权（或反向）、换取令牌路径多拼一段，都会在真正调用时才以 401 的形式暴露，而 401 又会被误判成令牌过期（案例 S4）。
- **怎么检查**：
  - `grep -n "积加\|jijia\|域名" src/settings.mjs src/providers.mjs`，确认存在成组校验并返回结构化失败。
  - 用接口验证：保存一个错配组合，必须返回 400 而不是 `ok:true`：
    `curl -s -X POST http://127.0.0.1:3211/api/admin/settings -H 'Content-Type: application/json' -b /tmp/probe.cookies -d '{"values":{"erp.baseUrl":"https://open.gerpgo.com/api/open","erp.authType":"basic"}}'`
  - 测试连接同样要拒：`POST /api/admin/settings/test` 带 `{"target":"erp","values":{...}}`，`ok` 必须为 `false` 且 `message` 指出错在哪。
- **违反后果**：配置错配在同步时才以 401 暴露，被当成令牌问题反复修（案例 S4）；用户看到的现象只是「数据不更新」，没有可动作的线索。

### R7 状态判定优先级固定，返回格式按参数准备
- **规则**：状态归一必须按固定优先级「最新节点 `status` → `ischeck=1` → 顶层 `state` → 文本正则」；解析必须同时支持 JSON 与 XML 及外层包装 `{ success, error_msg, track_data }`；智能识别凭据用 `key` 而不是 `customer`；接口失败不得覆盖最近一次有效状态。
- **为什么**：带 `show` 参数时快递100 返回 **XML**、不带才返回 JSON（原实现只认 JSON）；顶层 `state=2`「疑难」与最新轨迹节点 `status`「派件」不一致，按顶层判就把正常派件标成异常（案例 S6）。
- **怎么检查**：
  - `grep -n "text/xml\|<xml>" src/providers.mjs` 确认 XML 分支存在，且成功 / 失败两种 XML 都能解析。
  - 用例：正常派件中的快件不得被标成运输异常（PRD AC-005）；「接口失败不得覆盖最近一次有效状态」必须写成用例。
  - 凭据：`grep -n "customer" src/providers.mjs`，识别接口必须用 `key`（传 `customer` 会返回 `601 key过期`）。
  - 顶层码与节点冲突时，取一条真实单号核对最终状态确实来自最新节点 `status`。
- **违反后果**：报错「快递100 接口返回错误（错误码 无）：ok」——成功的 XML 被当成错误；正常派件被标成运输异常，违反 PRD AC-005（案例 S6）。

### R8 识别候选必须多来源
- **规则**：编码 / 公司候选队列 = 识别接口结果 → 上游原文公司名映射 → 同族编码扩展（去重、有界）；只在「公司参数异常」类错误（如 `408`）时换下一个候选；同族编码必须**实测确认存在**再写进映射表。
- **为什么**：识别接口只给 1 个候选（中通**快递** `zhongtong`），而这 3 票属中通**快运**，需 `zhongtongkuaiyun`；ERP 原值里其实写明了公司名并已提取进 `courier_name`，却只用于展示、没映射成查询用的 `courier_code`（案例 S5）。
- **怎么检查**：
  - `grep -n "zhongtongkuaiyun\|同族\|COURIER_FAMILY\|候选" src/providers.mjs` 确认映射表与扩展逻辑存在，且规则按「更具体在前」排列。
  - 换候选的条件必须限定在「公司参数异常」类错误，不得对所有错误无脑换（避免放大调用量）。
  - 新增同族编码前，先用一条真实单号实测该编码能返回结果（哪怕只是「暂无物流信息」），再写进映射表。
- **违反后果**：3 票 14 位 `7903…` 单号每轮失败、累计重试 **37 次**（按 30 分钟一轮约合一天 96 次无效查询）；用识别结果 `zhongtong` 查询报 `408 验证码错误`，换 `zhongtongkuaiyun` 才成功（案例 S5）。

### R9 失败单必须有最小重查窗口
- **规则**：查询失败的单号必须打上失败时间，并按最小重查窗口（实测 6 小时冷却）退出本轮队列；窗口结束后仍要优先重试，而不是永久放弃或每轮都重试。
- **为什么**：这两条路都会持续消耗限额：每轮重试（案例 S5 的 37 次、约一天 96 次无效查询）或永久失败后仍排在队首；需要「冷却 + 到期仍优先」的组合。
- **怎么检查**：
  - `grep -n "TRACKING_RETRY_COOLDOWN_HOURS" src/db.mjs`（当前 6），并确认取待查单号的 SQL 带 `last_error_at IS NULL OR last_error_at <= cutoff`。
  - 失败时写入失败时间：`grep -n "last_error_at" src/db.mjs`，`markSyncError` 与成功回写都要维护该列（成功时清空）。
  - 冷却生效后核对目标集合：同一批失败单在窗口内不出现在 `getShipmentsForTracking` 的结果里。
- **违反后果**：3 票 `7903…` 每轮失败累计 **37 次**，按 30 分钟一轮约合一天 96 次无效查询，白耗受限额度（案例 S5）。

### R10 契约测试必须用真实响应样本写
- **规则**：外部接口相关用例的输入必须是上游**真实抓到的响应**（状态码 + 响应体 + 业务码），不得用自己想象的形态；每条失败分支至少留一个真实样本，成功分支的多种返回格式（JSON / XML）各留一个。
- **为什么**：真实失败形态是 `HTTP 401 + code 40005 +「token已失效」`，而修复时的重试只写在「HTTP 200 + 业务码」分支、正则只匹配「鉴权失败」，于是**第一次修复线上完全没触发**（案例 S4）；返回格式随参数变化也让只按 JSON 写的用例永远绿（案例 S6）。
- **怎么检查**：
  - 测试里搜断言字段：`grep -rn "40005\|token已失效" test/`，失效应答必须有对应用例，而不是只有 `!response.ok` 的通用断言。
  - XML 与 JSON 两种成功响应各有用例：`grep -rn "<xml>\|track_data" test/providers.test.mjs`。
  - 新增分支时先在副本环境抓一次真实响应，把原文（可脱敏）贴进用例注释，再写断言。
- **违反后果**：修复上线后问题依旧（698 轮继续失败），并且「以为修好了」会延长故障时间（案例 S4、S6）。

## 二、检查清单（提交前逐条过）
- [ ] 全仓无空 `catch {}`；每个 catch 留下可读原因样本（≤10 条）
- [ ] 非 2xx 时先 `text()` 再判状态，上游 `code` / `messages` 出现在错误信息里
- [ ] 每轮结束检查 `result.failures` 并写日志；`sync_runs.error_summary` 非空
- [ ] 令牌失效后能回退自动换取；重试判定覆盖非 2xx 与业务码两条路径
- [ ] 换取令牌路径已归一化（不出现 `/api/open/api/open`）
- [ ] 同一上游的调用统一排队，间隔 ≥ `minIntervalMs`（600ms）；批量调用无 `Promise.all`
- [ ] 限流码（90008 / 509 / 文案）能触发指数退避，并用 mock 上游验证过
- [ ] 已探测并下推服务端筛选参数；无效参数记入「已实测无效」清单
- [ ] 预判与落库共用同一份判据（`orderFilterReason`）；逐单明细只对通过过滤的记录调用
- [ ] 所有同步入口共用互斥锁；重复触发返回 `skipped`，前端不假装成功
- [ ] 域名 + 鉴权 + 路径错配在保存与测试连接时被拒（400）
- [ ] 状态归一优先级固定（节点 status → ischeck → state → 正则），有 XML / JSON 双形态用例
- [ ] 接口失败不覆盖最近一次有效状态（有对应用例）
- [ ] 编码候选多来源 + 同族扩展（实测确认存在）
- [ ] 失败单有 6 小时冷却，成功后清除失败时间
- [ ] 失败分支的用例用的是真实响应样本（含 HTTP 状态 + 业务码 + 响应体）
- [ ] JSON 与 XML 两种成功响应各有一条用例，且都断言到最终状态

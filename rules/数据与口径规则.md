# 数据与口径规则

> 来源：工程案例集 D1–D6；每条都对应一次真实事故，后果写在条目里。
> 这个领域值得单独成文：复盘里「口径 / 规则不一致」13 条、「数据不正确 / 丢失」10 条，而「数据 / 接口 / 字段」是用户诉求第一大类（285 条，21%）——见 `../appendix/session-report.md`。
> 用法：可直接追加到项目 AGENTS.md，或作为提交前自查清单。
> 排序：按后果致命程度——先「永久丢数据」（R1–R3），再「用户看到错数字」（R4–R5），再「页面上看着没数据」（R6–R9），最后一条是执行纪律（R10）。
> 命令前置条件：涉及真实库的 SQL 都在**副本库**上跑（见 `../playbooks/改数据逻辑并在副本验证.md`）；`data/.probe-x.sqlite` 指副本库路径，请替换成你自己的。

## 一、必须

### R1 行级数据的主键必须取行级 ID
- **规则**：从上游「单据 + 明细」结构落库时，明细行主键必须用行级 ID（`poItemId` / `lineId`），并以数组下标兜底 + 单据号前缀做双保险；禁止用单据级 ID 当行主键。
- **为什么**：上游 `fid` / `id` 是**单据级** ID（同一交货单 6 行明细的 `fid` 全是 `54331`），行级唯一的是 `poItemId`，直接当行主键必然撞 `UNIQUE(erp_order_id, line_key)`（案例 D2）。
- **怎么检查**：
  - 副本库核对行级唯一性（差值必须为 0）：
    `sqlite3 data/.probe-x.sqlite "SELECT COUNT(*) - COUNT(DISTINCT erp_order_id || '|' || line_key) FROM order_items;"`
  - 看单张单据是否真的落了多行：
    `sqlite3 data/.probe-x.sqlite "SELECT erp_order_id, COUNT(*) c FROM order_items GROUP BY 1 HAVING c > 1 LIMIT 5;"`
    若恒为 1 行，说明明细被主键冲突挡在库外，而不是「本来就没有明细」。
  - 同步返回的 `failedCount` 必须为 0（修复后 `processedCount 123 → 164`、`failedCount 41 → 0`）。
  - 失败必须留样本：`grep -rn "failures" src/sync.mjs`，catch 里要记录失败单号与原因（最多 10 条）随结果返回。
- **违反后果**：每轮同步固定 **41 条**发货单入库失败（不是限流），这些单既没有明细也没有采购信息；外层 `catch {}` 只累加计数，导致问题长期无法诊断（案例 D2）。

### R2 删除父行前必须先把子行改指，禁止裸删
- **规则**：父表被 `ON DELETE CASCADE` 引用时，删除父行前必须在同一事务内先 `UPDATE` 子行的外键指向目标父行，再 `DELETE` 父行；去重合并靠 `UNIQUE` 约束驱动，不得用直接 `UPDATE` 撞唯一键。
- **为什么**：`erp_orders.shipment_id` 是 `ON DELETE CASCADE`，而 `promotePlaceholderShipment` 的冲突分支直接 `DELETE FROM shipments`，子行随之消失（案例 D5）。
- **怎么检查**：
  - 写删除语句前先枚举所有级联约束：
    `sqlite3 data/logistics.sqlite "SELECT sql FROM sqlite_master WHERE sql LIKE '%ON DELETE CASCADE%';"`
    逐条确认「这张父表的删除会带走哪些子表」。
  - 删除前后核对子行数：
    `sqlite3 data/logistics.sqlite "SELECT COUNT(*) FROM erp_orders WHERE shipment_id = <id>;"`
    删前必须已为 0（子行已迁走），不为 0 时停下来。
  - 事务形态必须是 `BEGIN` → 迁子行 → 删父行 → `COMMIT`，失败 `ROLLBACK`；参考 `src/db.mjs` 的 `promotePlaceholderShipment`。
- **违反后果**：占位单补上真实单号走合并分支时，该占位单上的**全部单据被删**，而调用方只重建当前一条；实测同一单号多票占位（`500284649696` 3 票、`800220897594` 4 票）正好走这个分支（案例 D5）。

### R3 外部字段落库前必须按形态校验，不得按长度判断
- **规则**：结构化字段也当外部输入处理，取值后先按目标形态校验（快递单号：`/^[A-Za-z0-9][A-Za-z0-9-]*$/`），不干净的值必须过提取/清洗流程；禁止用长度阈值决定是否清洗，禁止采信前缀猜出的公司名（公司名从原文提取）。
- **为什么**：`trackings` 实测是「公司名 + 单号」混串（`联昊通\t906571425039`、`诚旭物流：21121284`、`奥欣物流 5014235`），而字段路径写成 `let trackingNo = field` 原样返回，只有备注路径才过提取引擎（案例 D3）。
- **怎么检查**：
  - 副本库扫脏值条数：
    `sqlite3 data/.probe-x.sqlite "SELECT COUNT(*) FROM shipments WHERE is_placeholder = 0 AND tracking_no NOT GLOB '[A-Za-z0-9]*';"`
  - 或直接跑预演（只读）：
    `DATABASE_PATH=./data/.probe-x.sqlite node tools/repair-tracking-no.mjs`
    看输出的「单号形态不干净」条数。
  - 用例必须钉住短单号（如 `SF1`）不被送进提取引擎——第一版修复按长度判断，正是栽在这里；判据是「有没有非单号字符」而不是长度。
  - 上游字段抽样打印原文，确认形如 `公司名 + 分隔符 + 单号`，而不是假设字段名带 `trackingNo` 就是纯单号。
- **违反后果**：实测 **224 条**单号形如 `S66565296289顺心捷达`，交快递100 一律 `400 单号不是数字和字母组合`——页面上它们看起来「有单号」，问题被完美掩盖；后续需专项迁移（清洗 **129 条** + 合并 **10 组**，`erp_orders` **2524 条**关联零丢失）（案例 D3）。

### R4 一个业务概念只保留一处口径定义
- **规则**：统计、筛选、导出三处不得各写一遍同一个业务概念的判定条件；必须抽成一个可复用的谓词，其他位置只调用它。同一个词（如「未签收」）的全站定义只能有一处实现，且必须与需求文档原文一致。
- **为什么**：卡片用 `is_signed = 0 AND is_placeholder = 0`（PRD 写的是「全部未签收**且带快递单号**」），列表 `signed=false` 只过滤 `is_signed = 0`，占位单被算进未签收（案例 D1：卡片 **15**、列表 **173**，差 **158** 票）。
- **怎么检查**：
  - 全仓搜该概念的判定条件，同一概念命中超过 1 处即违规：
    `grep -rn "is_signed = 0" src/ public/ | grep -v test`
  - 跑口径断言脚本，要求全绿（关键项「列表条数 = 卡片数字」「列表里不出现待填写单号的行」）：
    `PROBE_BASE=http://127.0.0.1:3211 node .probe/verify-stat-card-filter.mjs`
  - 自相矛盾查询必须返回空集：`GET /api/shipments?signed=false&pending=true` 的 `total` 为 0。
  - 兼容旧参数时保留折算（旧链接参数不能直接报错），但折算结果仍要走同一处谓词。
- **违反后果**：点卡片看到的条数与卡片数字对不上（173 vs 15），用户按错数字做运营决策；修复前该断言 actual 2 / expected 1，说明两处口径已经在互相打架（案例 D1）。

### R5 状态维度必须互斥且完备
- **规则**：同一实体的各个状态维度必须满足「互斥 + 完备」：任一记录只能落在其中一个状态，所有状态之和必须等于全集；两个互相矛盾的状态组合必须返回空集而不是被悄悄放宽成一个 OR 条件。
- **为什么**：占位单（无单号）与未签收本是两个独立维度，纠缠后数字必然打架；把「卡片值 = 对应筛选 total」写成断言时 actual 2 / expected 1（案例 D1）。
- **怎么检查**：
  - 三态互斥加进用例：未签收 **15** + 待填写 **158** + 已签收 **38** = 全部 **211**（`.probe/verify-stat-card-filter.mjs` 里已有这一条断言）。
  - 矛盾组合必须为空：
    `curl -s "http://127.0.0.1:3211/api/shipments?signed=false&pending=true" -b /tmp/probe.cookies | head -c 200`
    返回的 `total` 必须是 0。
  - SQL 侧可直接核对互斥性：
    `sqlite3 data/.probe-x.sqlite "SELECT SUM(is_signed = 1 AND is_placeholder = 1) FROM shipments;"` 必须为 0。
- **违反后果**：概览数字与列表互相矛盾，用户对系统失去信任；「未签收」这一概念同时指两批数据（15 票与 173 票），报表口径不可复现（案例 D1）。

### R6 写 JOIN 前必须核对列语义并给出命中率
- **规则**：禁止凭列名相似写关联；必须先用上游真实响应确认「哪个接口同时返回这两个字段」，并在改链路前后各给出一次命中率数字（分子 / 分母）。
- **为什么**：SQLite 的 LEFT JOIN 在列不存在或值体系不同时不报错、只返回 null；上游 `msku` 是另一套编码（`S02452`），`productManagerAccount` 返回中文姓名而非账号（案例 D4）。
- **怎么检查**：
  - 每个新 join 附一条命中率 SQL，分子分母一起记录：
    `sqlite3 data/.probe-x.sqlite "SELECT COUNT(*) FROM order_items oi JOIN ref_products p ON p.sku = oi.seller_sku;"`
  - 自增 ID 与业务 ID 不得混用：`erp_orders.id` 是自增，`order_items.erp_order_id` 存的是业务 `erp_id`，误用会得出「428 条明细全是孤儿」的假结论（真孤儿为 0）。
  - 用「资料已同步」用例断言出**具体人名 / 站点**，而不是断言「不为 null」。
  - 命中率为 0 时必须当成缺陷处理，不得当作「上游没数据」结案。
- **违反后果**：运营 / 站点 / 部门三列长期全空；旧链路实测 `明细 seller_sku = ref_msku.msku` **0/116**、`shop_id = market.id` **0/539**、`managerAccount = username` 只有 **314/7728**（案例 D4）。修复后应达到 `product → products.sku` **108/108**、`姓名 → users.name` **7728/7728**、能关联出运营+部门的明细 **96/108**。

### R7 上游缺字段时不得用空值覆盖已有值
- **规则**：更新已有记录时，上游本次未返回的列必须保留旧值（`COALESCE(新值, 旧值)` 或「字段存在才写」），禁止用 `null` / 空串整行覆盖；同一行被多来源、多轮次写入时以「不丢已有信息」为约束。
- **为什么**：上游接口按单据类型返回的字段不同，一次缺字段的回写就会把上一轮已经拿到的值抹掉，表现为「明明同步过却显示空」（案例 D6 的同类根因：缺值处理不当导致 164 票里 22 票产品列整列空白）。
- **怎么检查**：
  - 看写入语句是否用 `COALESCE` 或显式列白名单：
    `grep -n "COALESCE" src/db.mjs | head`，`upsertErpOrder` 这类 upsert 必须保留旧值。
  - 抽查字段填充率不会被后一轮拉低：
    `sqlite3 data/.probe-x.sqlite "SELECT SUM(po_code IS NOT NULL AND po_code <> ''), SUM(supplier_name IS NOT NULL) FROM erp_orders;"`
    连跑两轮同步后，这两项不得下降。
  - 空态要有明确语义（「上游未返回」与「值确实为空」要能区分），不要用同一个空串表示。
- **违反后果**：已有数据被回写成空，页面看起来「同步失败」，实际是缺字段覆盖（案例 D6）；用户反馈「这列没数据」时需要先查排序与数据事实，再怀疑渲染。

### R8 聚合列必须有回退链，缺值不得让整块消失
- **规则**：列表聚合值必须按固定回退链取值（`asin → product_name → seller_sku → product`）并补查所需列；空态必须渲染一句说明，禁止用 `if (values.length)` 直接决定整个区块是否渲染。
- **为什么**：采购类明细（原料 / 辅料 / 包装）本就没有 ASIN，只收集 `item.asin` 会让 `asins.length` 为 0，整个产品区块（含运营 / 站点 / 部门）都不渲染（案例 D6）。
- **怎么检查**：
  - 用 SQL 量出「有明细但聚合为空」的条数：
    `sqlite3 data/.probe-x.sqlite "SELECT COUNT(*) FROM order_items WHERE (asin IS NULL OR asin = '') AND (product_name IS NOT NULL OR seller_sku IS NOT NULL);"`
  - 页面或探针脚本断言「产品列不出现整列 `—`」（有明细的 164 票里曾 **22 票**如此）。
  - 查渲染分支：`grep -n "if (asins.length)" public/app.js`，命中即违规。
- **违反后果**：产品列整列显示「—」，用户以为没同步，实际是渲染被条件跳过（案例 D6）。

### R9 排序必须显式把占位 / 无数据行沉底
- **规则**：默认排序必须把 `is_placeholder ASC` 作为第一顺位或强制次级键；时间列用 `COALESCE(last_track_at, updated_at)` 且不得让「刚同步」的占位行靠前；用户点选列排序时也必须拼上默认排序作为次级键。
- **为什么**：占位行没有 `last_track_at`，退回 `updated_at` 比较时它们刚同步完、时间最新，会把有轨迹的记录全挤到后面（案例 D6）。
- **怎么检查**：
  - 读 `ORDER BY` 生成逻辑：`grep -n "is_placeholder ASC" src/db.mjs`，必须出现在 `orderBy` 数组里
    （当前为 `['s.is_placeholder ASC', 's.is_signed ASC', 's.is_exception DESC', 'COALESCE(s.last_track_at, s.updated_at) DESC']`）。
  - 首屏抽查：连续翻 3 页，断言「待填写快递单号」不占据首屏（此前首页 20 行全是它）。
  - 用户报「某列全空」时，先按这个顺序查：排序 → 数据事实 → 渲染，不要直接改样式。
- **违反后果**：同步完成后「快递 / 状态 / 最新轨迹 / 更新」看着全空，首页 20 行全是「待填写快递单号」（案例 D6）。

### R10 数据修复分两步：先修代码缺陷，再跑补数
- **规则**：补数 / 迁移 / 清库脚本必须默认 dry-run，先输出「将影响多少行、会走哪条分支」，确认后才 `--apply`；若 dry-run 显示会走合并 / 删除分支，必须先修掉对应缺陷再执行；`--apply` 前必须已有一致性备份。
- **为什么**：D5 的合并分支缺陷正是被补数动作触发的——补数本身没错，错在缺陷还在（案例 D5：「先修缺陷、再跑补数」）。
- **怎么检查**：
  - 无 `--apply` 时脚本必须只读：跑一次，随后 `sqlite3` 核对各表 `COUNT(*)` 与跑前一致。
  - 输出必须给出分支与条数（如 `tools/reset-business-data.mjs` 的「将要清空的表」、`tools/repair-tracking-no.mjs` 的清洗 / 合并 / 降级三类计数）。
  - 写库前确认备份已生成且可用：
    `sqlite3 -cmd ".timeout 15000" data/logistics.sqlite "VACUUM INTO 'data/logistics.bak-<时间戳>.sqlite';"`
    随后 `PRAGMA integrity_check;` 必须输出 `ok`。
- **违反后果**：直接在生产执行补数，占位单上的单据被级联删掉且没有回滚点，只能靠备份回捞（案例 D5）。

## 二、检查清单（提交前逐条过）
- [ ] 明细行主键是行级 ID；`COUNT(*) - COUNT(DISTINCT 行键)` = 0；`failedCount` = 0 且有失败样本
- [ ] 删除父行前已枚举 `ON DELETE CASCADE` 子表，并在事务内先迁子行再删
- [ ] 外部字段按形态正则校验（单号 `^[A-Za-z0-9][A-Za-z0-9-]*$`），有用例放过 `SF1` 这类短单号
- [ ] 同一业务概念在全仓只有一处判定条件（grep 命中 ≤1 处）
- [ ] 口径断言脚本全绿：卡片数字 = 对应筛选 `total`；三态相加 = 全部
- [ ] 矛盾状态组合（`signed=false&pending=true`）返回空集
- [ ] 每个新 join 都有命中率数字（分子 / 分母），且分母非 0
- [ ] upsert 保留旧值（`COALESCE`），连跑两轮后字段填充率不下降
- [ ] 每个聚合列都有回退链，空态有文案而不是整块消失
- [ ] `ORDER BY` 含 `is_placeholder ASC`，首屏不出现成排占位行
- [ ] 补数 / 清库脚本先跑无参 dry-run，输出条数与分支
- [ ] 任何写库操作前已确认存在 `VACUUM INTO` 备份且 `integrity_check` = ok

# 测试与验收规则

> 来源：工程案例集 T1–T4；每条都对应一次真实事故，后果写在条目里。
> 用法：可直接追加到项目 AGENTS.md，或作为提交前自查清单。
> 适用栈：`node --test`（vm + DOM stub）+ Playwright 真实浏览器 E2E（`npm run test:browser`）+ 真实进程测试。

## 一、必须

### R1 改动前先取证：先量后改，改前改后量值一起交付
- **规则**：UI / 样式 / 布局改动前，必须用浏览器取到真实计算样式与几何数字（`getComputedStyle` / `getBoundingClientRect`）再动手；交付时必须给出改前与改后的同一量值。禁止凭读源码或推测位置直接改。
- **为什么**：必填星号换行按「推测的位置」精准修了两轮都没修好，第三轮改成不依赖位置假设的 `flex-wrap: nowrap` 才生效；`.detail-title` 只有 `align-items: center` 而没有 `display: flex`，对块级元素完全无效，`674px` 单列 grid 里两个小元素于是分两行（案例 T3）。
- **怎么检查**：
  - 交付里必须有「改前 X px → 改后 Y px」两个数字（例如导航按钮 48 → 36；表格按钮 30 / 导航 36 / 账户 40 这类同档位值要成组给出）。
  - 浏览器控制台取实际值并贴进回报：`getComputedStyle(el).display`、`el.getBoundingClientRect().height`。
  - 只有「已对齐」「已修复」这类措辞 = 未取证，退回重做；远程协作时第一时间索取截图。
- **违反后果**：两轮修复全部打在错误位置，第三轮才命中真因（案例 T3）。

### R2 vm 单测与真实浏览器测试分工，禁止用 stub 冒充 DOM 行为
- **规则**：vm + DOM stub 只用于纯函数、渲染字符串、URL/参数拼装；shadow DOM 事件、`FormData` 取值、焦点陷阱、背景滚动锁、键盘可达性、控件等高、窄屏溢出与折行必须用真实浏览器测试。给 stub 派发事件必须补 `target`（真实 DOM 事件必有 target）。
- **为什么**：drawer 测试桩的 `querySelector` 永远返回新建的空 div，断言拿不到真实文本；换组件后真正可聚焦的节点跑进了 shadow DOM —— stub 测的只是桩本身（案例 T1）。
- **怎么检查**：
  - `grep -n 'querySelector\|createElement' test/*.test.mjs`，看 stub 是否在承担几何/事件断言；是则必须搬到浏览器测试。
  - 两套测试都要跑且都要过：`npm test`（实测 `tests 274 / pass 274 / skipped 0`）与 `npm run test:browser`（断言数 68 → **108**）。
  - 交叉核对（实测两者相等，均为 **274**）：`grep -hc "^test(" test/*.test.mjs | awk '{s+=$1} END {print s}'` 的输出必须等于 `npm test` 报的 `tests` 数；小于它说明有测试文件没被跑到。
  - 任何一条 UI 断言只存在于 vm 单测里，视为无效。
- **违反后果**：单测全绿而上线仍不可用 —— 焦点、溢出、等高这类问题全部漏到用户侧（案例 T1）。

### R3 E2E 临时库与密钥必须按端口隔离，禁止共用固定路径
- **规则**：E2E 的 `DATABASE_PATH` 与 `SECRET_KEY_PATH` 必须含运行端口（如 `.e2e-<PORT>.sqlite` / `.e2e-<PORT>.key`）；测完清理，不留固定名的临时库。
- **为什么**：两个端口并发跑共用 `data/.e2e.sqlite`，一方启动时删库、另一方正在写 → `attempt to write a readonly database` 的假失败（案例 T2）。
- **怎么检查**：
  - `grep -n 'e2e' tools/browser-e2e.mjs | grep -i 'DB_PATH\|KEY_PATH'` 确认路径含 `${PORT}`。
  - 两个端口同时跑：`E2E_PORT=3210 npm run test:browser & E2E_PORT=3211 npm run test:browser`，两边都不得出现 readonly / database is locked。
  - `ls data/.e2e*` 不应残留固定名文件；残留会让下一次运行拿到上一次的数据。
  - 例：路径形如 `data/.e2e-3210.sqlite` 与 `data/.e2e-3210.key`，`E2E_PORT` 一变就整体换一套。
  - 每次运行前先删掉本端口自己的临时文件，避免上一次运行的残留数据影响本次断言。
- **违反后果**：并发跑测试必然随机假红，时间消耗在排查测试基础设施而不是产品缺陷上（案例 T2）。

### R4 等待条件替代固定 sleep，断言写成「等高 + 区间」
- **规则**：等待必须用 `waitForFunction` / 轮询条件，禁止 `waitForTimeout` 之类固定 sleep 决定断言时机。几何断言写「同档位等高 + 合理区间」，禁止钉死像素；计时类容差 ≥ 20ms。
- **为什么**：固定等待抢跑（宽度有 200ms 过渡）；断言钉死 43px 而实际 42px、账户 40px 而实际 41px；限流用例 gap 实测 112~128ms 配 5ms 容差随机变红（案例 T2）。
- **怎么检查**：
  - `grep -rn 'waitForTimeout\|setTimeout' tools/browser-e2e.mjs test/*.mjs`，断言路径上不得出现；有则换成条件轮询。
  - 例：等控件宽度稳定用 `await page.waitForFunction(() => el.getBoundingClientRect().width === 200)`，而不是 `await page.waitForTimeout(500)`。
  - `grep -rn 'assert.equal(.*height\|=== 4[0-9]' test/*.mjs tools/browser-e2e.mjs`，把像素相等断言改写成区间（38–46px）或「与同组控件等高」。
  - 连续跑 5 次 `npm run test:browser`，不得出现抖动红；出现一次就说明容差还不够。
- **反面示例**：限流用例断言「两次调用间隔 ≥ 500ms」，实测 gap 112~128ms 配 5ms 容差 → 随机变红；容差放宽到 20ms 后仍能抓到「完全没限流」。
- **违反后果**：假红持续消耗排查时间，并让「真的没限流」这类问题被误判为通过（案例 T2）。

### R5 fixture 必须取自真实数据形状，修复缺陷时同步改掉固化缺陷的旧断言
- **规则**：mock / fixture 必须覆盖真实库里的取值分布；修复缺陷时必须搜索并改写「把缺陷当正确行为」的旧断言。
- **为什么**：mock 数据永远满足渲染条件，而真实库 180 条全是 `delivery`，两个区块从未渲染；旧断言写着「销售发货单不显示采购信息」，等于把缺陷固化进测试（案例 T2）。
- **怎么检查**：
  - 先拿真实库跑取值分布：`node -e "const{DatabaseSync}=require('node:sqlite');const d=new DatabaseSync('data/logistics.sqlite',{readOnly:true});console.log(d.prepare('SELECT transport,COUNT(*) c FROM erp_orders GROUP BY transport').all())"`。
  - fixture 里必须出现这些取值；否则补上。
  - 修复缺陷后 `grep -rn '<被改掉的旧行为>' test/ tools/`，确认没有断言还在保护旧行为。
- **反面示例**：旧断言「销售发货单不显示采购信息」把缺陷写成了规格，导致该问题长期假绿（案例 T2）。
- **违反后果**：测试长期假绿，缺陷区块直到用户侧才暴露（案例 T2）。

### R6 E2E 脚本必须无残留状态：用完即关、每个用例自带前置
- **规则**：E2E 每个用例结束后必须关闭自己打开的浮层/弹窗，并清掉自己创建的数据；禁止依赖上一步的界面残留状态。
- **为什么**：创建账号弹窗故意保留，遮住删除弹窗的按钮导致脚本自身崩掉，报出的是脚本缺陷而不是被测缺陷（案例 T2）。
- **怎么检查**：
  - `grep -n 'showModal\|\.show()' tools/browser-e2e.mjs`，每处都要能找到配对的关闭/`hide()`。
  - 把单个用例单独跑（临时只保留该用例）也必须通过，不得因为它排在某个用例之后才通过。
  - 例：新建账号弹窗测完必须显式关闭，否则它会遮住删除弹窗的按钮，让后一个用例崩在脚本自身缺陷上。
- **违反后果**：脚本自身崩溃被当成产品缺陷，排查方向整体跑偏（案例 T2）。

### R7 排查环境/配置类问题时必须走统一读取函数，禁止自建直读脚本
- **规则**：调试脚本取配置必须走 `readSettings` / `readEffectiveSettings`（负责类型转换与归一化的那一层），禁止自己 `SELECT` 出原始值直接喂给构造函数。
- **为什么**：诊断脚本把库里的字符串 `"true"` 直接喂给配置构造函数，因 `"true" !== true` 落回演示分支，得到「0 条轨迹」的假象（案例 T3）。
- **怎么检查**：
  - `grep -rn 'readSettings\|readEffectiveSettings' tools/*.mjs` 确认取配置处都走这两个函数。
  - 用 `grep -n 'settings' tools/*.mjs` 找绕过统一读取函数的出口并改掉。
- **反面示例**：诊断脚本把字符串 `"true"` 直接喂给配置构造函数，`"true" !== true` 使其落回演示分支，得出「0 条轨迹」的假象（案例 T3）。
- **违反后果**：得到与真实运行不同的结论，并据错误结论继续排查（案例 T3）。

### R8 多会话并发编辑：只做局部 edit、编辑前重读、改完复核自己的改动仍在
- **规则**：只允许局部 `edit`（`old_string` 唯一匹配），禁止整文件 `write` 覆盖；每次编辑前重新 `read` 并看 mtime；改完立刻复核自己的改动仍存在。端到端只断言本功能负责的契约（如「不因权限被拒」而不是「一定 200」），看到别人的半成品先复核文件当前内容再下结论，不擅自替对方改。
- **为什么**：反复出现 `file changed since it was read`；`app.js` 在一次阅读期间从 1363 → 1412 → 1430 行；测试总数 199 → 214 → 231 → 262 → 274 持续漂移；别人的中间态（`ref_msku.market` 缺列、`app.js` 语法未补完）制造「假红灯」（案例 T4）。
- **怎么检查**：
  - 改完立刻三条命令：`grep -n '<你新增的标识>' <file>`（改动还在）、`node --check <file>`（语法完整）、`npm test`（实测 274/274、`skipped 0`）。
  - 编辑工具返回「file changed since it was read」时必须重读再改，不得原样重试同一 `old_string`。
  - 端到端断言里不得出现与权限无关的「一定 200」。
- **违反后果**：整文件写入吃掉他人改动，一次阅读期间的并发修改静默丢失（案例 T4）。

### R9 报告测试结果必须给 `skipped` 与总数，禁止把 skipped 当通过
- **规则**：测试结论必须引用命令输出的 `ℹ tests` / `ℹ pass` / `ℹ skipped` 三行原值，且 `skipped` 必须为 0；禁止只回报「通过」，禁止引用文档或记忆里手写的旧数字。
- **为什么**：跳过就是没验；`test/health-exposure.test.mjs` 里的局域网断言在本机没有非回环 IPv4 时会 `t.skip`（防火墙拦截时也会），只报「通过」会把「根本没验」当成果（案例 T4：测试总数持续漂移，口头数字不可信）。
- **怎么检查**：
  - `npm test 2>&1 | tail -8`，输出里必须 `fail 0` 且 `skipped 0`。
  - `npm run test:browser` 输出末尾 `通过 N / M`，N 必须等于 M。
  - 若 `skipped > 0`，必须在回报里写明跳过原因与补救方式（例如换一台有局域网地址的机器重跑，或临时接一个非回环网卡）。
  - 禁止把「本机没有非回环 IPv4」这类跳过写成「已通过」。
- **违反后果**：以「测试全绿」交付，实际关键分支一次都没跑（案例 T4）。

### R10 进程级测试必须有就绪门与端口冲突检测，禁止固定等待启动
- **规则**：真实进程测试（spawn 服务后断言）必须：① 先检测端口是否被占用，占用即报错退出；② 用轮询 + 超时的就绪门（≤ 20 秒）等待 `/api/health` 返回 200；③ 结束时 `SIGKILL` 子进程并删除临时目录。
- **为什么**：端口被占用或服务启动慢会让断言打在「还没监听」上，报出的是环境问题而不是产品缺陷；`test/health-exposure.test.mjs` 的 `waitReady`（20 秒 deadline + 150ms 轮询）与 `tools/browser-e2e.mjs` 的端口占用检查就是这个模式（案例 T2）。
- **怎么检查**：
  - `grep -n 'waitReady\|deadline\|已被占用' test/*.mjs tools/browser-e2e.mjs`，三处都要命中。
  - `grep -n 'SIGKILL\|after(' test/health-exposure.test.mjs` 确认有清理。
  - 先手动占用端口再跑测试，应看到明确的「端口已被占用」提示，而不是随机断言失败。
  - 就绪门必须有超时上限（本仓库为 20 秒）并在超时时给出明确失败信息，不能无限等。
- **反面示例**：断言打在服务还没监听的时刻，报出的是环境问题而不是产品缺陷，排查方向被带偏（案例 T2）。
- **违反后果**：测试结果取决于机器负载与残留进程，本地绿、换机红（案例 T2）。

## 二、检查清单（提交前逐条过）

- [ ] 交付里有 UI 改动的「改前 → 改后」量值（像素/尺寸数字），不是「已修复」（R1）
- [ ] 纯函数与渲染结构用 vm 单测；shadow DOM 事件/焦点/等高/溢出用真实浏览器（R2）
- [ ] E2E 临时库与密钥路径含端口；两端口并发跑不出 readonly / locked（R3）
- [ ] 断言路径上没有固定 `waitForTimeout`；像素断言已改成「等高 + 区间」；计时容差 ≥ 20ms（R4）
- [ ] fixture 覆盖真实取值分布；被修复的旧缺陷没有残留断言（R5）
- [ ] E2E 每个用例自开自关，单独跑也能通过（R6）
- [ ] 调试脚本取配置走 `readSettings` / `readEffectiveSettings`（R7）
- [ ] 本次改动全部用局部 edit；改完 `grep` + `node --check` + `npm test` 三连复核通过（R8）
- [ ] 回报里给出 `tests 274 / pass 274 / skipped 0`，浏览器测试 `通过 N / M` 且 N = M（R9）
- [ ] 真实进程测试有端口占用检查 + 就绪门（≤20s 轮询）+ 结束时 SIGKILL 与清理（R10）

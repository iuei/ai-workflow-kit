# 进程与部署规则

> 来源：工程案例集 P1–P5；每条都对应一次真实事故，后果写在条目里。
> 用法：可直接追加到项目 AGENTS.md，或作为提交前自查清单。
> 适用栈：单进程常驻 Node 服务（本仓库为 `node src/server.mjs` + `node:sqlite` 单文件库 + 无构建原生前端）。

## 一、必须

### R1 工作目录必须是项目根，Node 必须 ≥ 22.5.0
- **规则**：常驻服务的 `WorkingDirectory` / `cwd` 必须等于项目根（`src/config.mjs` 用 `process.cwd()` 解析 `.env`、`data/`）；运行时 Node 必须 ≥ 22.5.0（项目用内置 `node:sqlite`）。禁止依赖命令行默认的 `node`／`pm2`。
- **为什么**：目录设错会静默新建一个空库，表现为「登录成功但一条数据都没有」；Node 16/18/20 启动直接报 `Cannot find module 'node:sqlite'`（案例 P5）。
- **怎么检查**：
  - `node -v` 输出版本号；再验模块可用：`node -e "require('node:sqlite');console.log('sqlite-ok')"` 必须打印 `sqlite-ok`（宝塔上用绝对路径，如 `/www/server/nodejs/v22.22.3/bin/node`）。
  - 确认进程用的是哪一份库：`lsof -p "$(lsof -ti tcp:3000)" | grep -c 'data/logistics.sqlite'` 必须 ≥ 1；为 0 说明它在别处新建了空库。
- **违反后果**：启动即失败；或「登录成功、数据为空」的静默假象（案例 P5）。

### R2 迁移必须「库 + 密钥文件」成套，数据包用一致性快照
- **规则**：`.settings.key`（或 `SECRET_KEY_PATH` 指向的文件，默认 `./data/.settings.key`）必须与数据库一起搬、一起备份、一起恢复。取数据包必须用 `VACUUM INTO` 生成快照，禁止在服务运行中 `cp` 数据库文件。权限 `600`。
- **为什么**：接口凭据（customer / key / appSecret）是 AES 加密入库的，密钥文件是唯一解密凭据，丢失不可恢复；直接复制正在写的 SQLite 会拿到不一致快照（案例 P5）。
- **怎么检查**：
  - 快照一致性：`node -e "const{DatabaseSync}=require('node:sqlite');const d=new DatabaseSync('data/logistics.sqlite',{readOnly:true});console.log(d.prepare('PRAGMA integrity_check').get())"` 期望 `{integrity_check:'ok'}`。
  - 权限：`ls -l data/.settings.key` 期望 `-rw-------`；不是就 `chmod 600 data/.settings.key`。
  - 成套性：上线后打开「接口配置」页，customer / key / appKey 必须是掩码（如 `DE••••34`）而不是空白或报错 —— 这一条同时证明两个文件配套。
- **违反后果**：只搬库导致接口配置页全部解不开，所有密钥必须重填；密钥丢失则不可恢复（案例 P5）。

### R3 一个进程只能有一个实例，自启前先停手动实例
- **规则**：注册开机自启/守护（launchd `KeepAlive`、PM2）之前，必须先停掉手动 `nohup`／前台实例；禁止守护进程与手动实例并存。
- **为什么**：`KeepAlive` 与手动实例抢端口，launchd 报 `Bootstrap failed: 5` 并无限重启（案例 P5）。
- **怎么检查**：
  - `pgrep -fl 'src/server.mjs'` 必须只有一行；`lsof -ti tcp:3000` 必须只有一个 PID。
  - 注册后：`launchctl print gui/$(id -u)/com.logistics.monitor | grep -E 'state|pid'` 状态为 `running`（宝塔「Node 项目」列表显示「运行中」）。
  - 若 launchd 报 `Bootstrap failed: 5`，先回到上一步 `pkill` 再注册。
- **违反后果**：进程无限重启、端口反复失守，用户侧表现为服务持续中断（案例 P5）。

### R4 守护配置必须写绝对路径并把 stdout/stderr 落盘
- **规则**：自启/守护配置里，可执行文件与脚本路径必须写绝对路径（不得依赖 PATH 里的 `node`），必须显式设置工作目录、必须把 stdout 与 stderr 同时重定向到 `data/server.log`。
- **为什么**：宝塔的 Node 版本管理器在「命令行版本未设置」时 `node`/`pm2` 不在 PATH，相对路径与 PATH 依赖会让守护拉起失败；没有输出重定向则启动失败只剩一个退出码，无从定位（案例 P5、P2）。
- **怎么检查**：
  - `grep -n 'ProgramArguments' -A3 deploy/com.logistics.monitor.plist`：`node` 路径与脚本路径两行都必须是绝对路径。
  - `grep -n 'StandardOutPath\|StandardErrorPath\|WorkingDirectory' deploy/com.logistics.monitor.plist`：三项齐全且都指向项目内绝对路径。
  - 重启后 `ls -l data/server.log` 的 mtime 必须是本轮 —— mtime 没动说明输出根本没落盘。
- **违反后果**：launchd/PM2 静默拉起失败，或启动失败无任何可读日志（案例 P5、P2）。

### R5 改了服务端代码必须重启并贴出启动日志时间戳
- **规则**：必须重启常驻进程，并在回报里附上「新进程启动时间 + 启动成功日志行」。禁止用「文件已保存」代替「已生效」。本项目 `package.json` 的 `start` 是 `node src/server.mjs`（常驻、非 `--watch`），`dev` 才是 `node --watch src/server.mjs`。
- **为什么**：模块在进程启动时载入，改 `src/` 下任何文件都不影响已在跑的进程（案例 P3：「刷新页面没有变化」「新列点了没反应」）。
- **怎么检查**：
  - 进程启动时间：`ps -o lstart=,command= -p "$(lsof -ti tcp:3000)"`，必须晚于最后一次源码 `mtime`（`ls -lT src/server.mjs public/app.js`）。
  - 启动日志：`tail -n 20 data/server.log` 里要有本轮的 `物流数据监控系统运行于 http://localhost:3000（ERP=…，快递100=…）`。
  - `src/server.mjs` 启动时只打印一次该行，出现两次就是重复拉起（对照 R3）。
- **违反后果**：用户在旧进程上复测，把「没生效」当「改错了」，交接文档里「重启」被反复提醒 **49 次**（案例 P3）。

### R6 前端资源版本号必须能自证「你加载的是哪一版」
- **规则**：必须让 `index.html` 引用的自有 JS/CSS 带随文件变化的版本参数，并在页面可见处显示界面版本。禁止把 `src="/app.js"` 这类固定地址直接吐给浏览器。
- **为什么**：固定地址无法区分「缓存旧文件」与「代码没改」（案例 P3：缓存出现 14 次，用户只会说「刷新了没变化」）。
- **怎么检查**：
  - `curl -s http://127.0.0.1:3000/ | grep -o 'app.js?v=[0-9]*'` 记下数字 → `touch public/app.js` → 再取一次，两个数字必须不同。
  - 同一响应里的 `styles.css` / `sidebar.css` 也要带 `?v=`。
  - 页面可见处（如页脚或「关于」）应有界面版本，用户报障时可一步核对。
- **违反后果**：用户按旧 JS 复测并进一步误判后端，一轮排查全程白跑（案例 P3）。

### R7 缓存策略必须显式声明：自有资源 `no-store`，第三方 vendor 才长缓存
- **规则**：`index.html` 与自有 JS/CSS 必须 `Cache-Control: no-store`；只有版本固定的第三方组件目录（`/vendor/`）才允许 `max-age` 长缓存 + `immutable`。升级组件库必须改目录名或加版本参数，禁止原地覆盖同名文件。
- **为什么**：自有资源被浏览器或中间层缓存后，用户「刷新」也只会拿到旧 JS，表现为「改了代码但页面没变化」（案例 P3）。
- **怎么检查**：
  - `curl -sI http://127.0.0.1:3000/app.js | grep -i cache-control` → 必须是 `no-store`。
  - `curl -sI http://127.0.0.1:3000/vendor/shoelace/shoelace.js | grep -i cache-control` → 含 `immutable`。
  - 若装了宝塔「网站加速」类插件，需确认它没有改写这两个响应头（对比直连 3000 与经 Nginx 的同一个头）。
- **违反后果**：每次交付都可能被旧缓存掩盖，排查先花在「是不是没生效」上（案例 P3）。

### R8 组件资源基路径必须钉死在本机，部署后外部域名请求为 0
- **规则**：自托管组件库必须显式钉死资源根路径 —— `public/index.html` 里 `<script data-shoelace="/vendor/shoelace">`，并由 `public/ui-vendor-path.js` 调 `setBasePath('/vendor/shoelace')` 兜底。禁止依赖组件库的 CDN 回落。
- **为什么**：Shoelace 的 basePath 找不到 script 标签就回落到官方 CDN，内网部署时下拉箭头、复选框对勾、弹窗关闭图标全部 404（案例 P5）。
- **怎么检查**：`grep -n 'data-shoelace' public/index.html` 与 `grep -n 'setBasePath' public/ui-vendor-path.js` 两处都要命中；浏览器 E2E 输出「外部域名请求（内网部署必须为 0）」下面必须是 `（无）`，或 `E2E_PORT=3210 npm run test:browser 2>&1 | grep -A2 '外部域名请求'`。
- **违反后果**：内网机器上全部组件图标 404，界面看起来「样式全坏」，实际是资源路径问题（案例 P5）。

### R9 启动阶段的引导逻辑必须包异常，进程无论如何都要 listen
- **规则**：`server.listen()` 之前的任何引导任务（引导同步、初始化管理员、历史数据迁移）必须各自 try/catch，异常只记日志，禁止让异常逃到顶层 await。禁止把阶段 A 与阶段 B 写成「A 抛错就跳过 B」的串行无保护链。
- **为什么**：启动引导同步原是顶层 await 且无 try/catch，一次上游限流就让进程 exit 1、端口始终不监听；`syncAll` 里资料接口 509 又让轨迹阶段被跳过（案例 P2）。
- **怎么检查**：`grep -n -B2 -A4 'await .*sync\|await ensure' src/server.mjs` 确认每处都在 try 内；复现法：把 ERP 配成「已启用但地址不可达」并清空 `shipments`，重启后进程仍须监听 3000，日志出现「启动引导同步失败（服务继续启动…）」。
- **违反后果**：上游一次失败 = 服务彻底起不来；另一形态是「物流单正常入库但一条轨迹都没有」（案例 P2）。

### R10 口令类信息只对回环来源回显，生产必须走显式凭据
- **规则**：任何返回口令/密钥/令牌的接口必须按来源判定，只对回环地址回显；判定必须是「`::1` 或 `127.` 前缀或 `::ffff:127.` 前缀」，禁止只比 `127.0.0.1`。生产环境必须设置 `APP_USERNAME` + `APP_PASSWORD`，使演示分支（`config.isDemoAuth`）为 false。
- **为什么**：`/api/health` 曾对任何来源回显 `demo/****`，而服务监听 `0.0.0.0`，同网段任何人一个匿名 `curl` 即拿到可用管理员凭据（实测可登录并读写 `/api/admin/settings`）（案例 P1）。
- **怎么检查**：`npm test` 中 `test/health-exposure.test.mjs` 必须通过且 `skipped=0`（跳过等于没验）；手工复核 `LAN=$(ipconfig getifaddr en0)` → `curl -s http://$LAN:3000/api/health` 返回里 `demoAccount` 应为 `null`；`curl -s http://127.0.0.1:3000/api/health | grep -o '"isDemo"[^,]*'` 在生产应为 `false`。
- **违反后果**：内网任何一台机器匿名请求即获得管理员凭据，后台等于公开（案例 P1）。

### R11 反向代理场景禁止依赖「来源地址」做安全判断
- **规则**：位于 Nginx/网关之后时，不得把 `socket.remoteAddress` 当访问者身份（它会变成代理自身的 `127.0.0.1`，判断退化为「总是本机」）。安全边界必须落在显式配置上：生产 `.env` 写死账号口令、管理接口未登录一律 401、3000 端口不对公网放行。
- **为什么**：回环判断在反代后退化为恒真，P1 的兜底就只剩「配了 `APP_USERNAME`」这一条（案例 P1）。
- **怎么检查**：`curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/admin/settings`（无 Cookie）必须 401；`curl -s http://127.0.0.1:3000/api/health | grep -o '"demoAccount":[^,]*'` 应为 `null`。
- **违反后果**：演示口令在生产通过反代被任意匿名请求取走，加密存储等设计全部被绕过（案例 P1）。

### R12 启动/定时任务的失败必须进日志，禁止只写库
- **规则**：所有 `catch` 必须 `console.error` 一条可定位的信息（阶段名 + 上游 code + 失败样本，样本上限 10 条）。禁止 `catch {}` 静默、禁止只累加计数。启动引导同步与定时同步都要显式检查 `result.failures` 并打日志。
- **为什么**：定时同步每 20.0 分钟精确失败一轮、累计 **698 轮**、数据冻结 2 天，日志里只有 `sync_runs` 一行，只能靠猜；`catch {}` 让每轮固定 **41 条**失败单无法诊断（案例 P2、S4、D2）。
- **怎么检查**：`grep -rn 'catch\s*{' src/*.mjs` 找空 catch；`grep -n 'failures' src/server.mjs` 确认启动与定时两条路径都打了；改完后重启进程，`tail -n 50 data/server.log` 必须能看到你自己的新日志行（不是只在表里多一行）。
- **违反后果**：故障静默数天（43.8 小时完全无同步记录）才被发现，期间所有数据冻结（案例 P2、S4）。

### R13 配置的默认值必须与存量业务数据同步迁移，并按完整 key 写入
- **规则**：改动任何字段 `default` 时，必须同时改已有库中的存量值；写入必须用完整 key（如 `tracking.pollIntervalMinutes`），禁止写顶层便捷回显字段。禁止认为「改了默认值就等于改了配置」。
- **为什么**：默认值只在「从未保存过这一项」时生效；把自动同步改成 30 分钟时 `PUT` 返回 `ok:true, saved:0` 静默不生效（案例 P4）。
- **怎么检查**：写入后回读核对：`curl -s -b cookie.txt http://127.0.0.1:3000/api/admin/settings | grep -o '"tracking.pollIntervalMinutes":[0-9]*'`；响应里 `saved` 不得为 `0`；配置页顶部提示必须显示新间隔数字。
- **违反后果**：界面显示与实际轮询不一致，用户以为改好了而系统仍按旧值跑（案例 P4）。

### R14 配置校验必须在「已保存 + 本次补丁」合并后的生效配置上做
- **规则**：组合校验（如「启用快递100 前必须填 customer」）必须读取 `readEffectiveSettings()` 与本次补丁合并后的结果，禁止只校验本次提交的局部补丁。敏感字段留空（`''`）= 保持原值，显式 `null` = 清空，两种语义都要支持。
- **为什么**：加密字段在补丁里是空串，被当成「未填」→ 只保存 ERP 卡片却被拦、整个配置页写不进去；且填错的凭据永远撤不掉（案例 P4）。
- **怎么检查**：只提交 ERP 卡片（带一个空的敏感字段）应返回成功；对某敏感字段提交 `null` 后回读该字段必须为空；`grep -n 'normalizePatch\|readEffectiveSettings' src/server.mjs` 确认校验入口用的是合并结果。
- **违反后果**：配置页整页无法保存；错误凭据永久残留，审计里还留有明文历史（案例 P4）。

### R15 诊断与迁移脚本必须开只读连接或独立库，禁止直连生产库改写
- **规则**：排查用的诊断脚本对生产库必须用 `new DatabaseSync(path, { readOnly: true })` 打开；会写数据的脚本（清洗、补数）必须先 `VACUUM INTO` 出快照、默认 dry-run，并另起独立库或独立进程，禁止与服务主进程共用同一个数据库文件。
- **为什么**：服务与脚本同时写同一个 SQLite 会互相锁死或写入不一致；占位单合并分支曾把整票单据级联删掉，补数脚本 dry-run 与「先修缺陷、再跑补数」的顺序是靠快照与隔离才守住数据的（案例 D5、P5）。
- **怎么检查**：`grep -n 'readOnly' tools/*.mjs` 确认诊断脚本都带该选项；`grep -n 'VACUUM INTO\|dryRun\|dry-run' tools/*.mjs` 确认写脚本有快照或 dry-run 开关；执行前 `lsof data/logistics.sqlite` 确认没有第二个写者。
- **违反后果**：生产数据被脚本静默改写或整票删除；库被锁导致服务请求失败（案例 D5、P5）。

## 二、检查清单（提交前逐条过）

- [ ] `node -v` ≥ 22.5.0、`node -e "require('node:sqlite')"` 通过、进程工作目录是项目根（R1）
- [ ] 数据包由 `VACUUM INTO` 生成，`integrity_check = ok`，`.settings.key` 与库成套且权限 600（R2）
- [ ] `pgrep -fl 'src/server.mjs'` 只有一行，注册自启前已停手动实例（R3）
- [ ] 守护配置用绝对路径、含 `WorkingDirectory` 与 stdout/stderr 重定向，日志 mtime 是本轮（R4）
- [ ] 改了 `src/` 下任何文件 → 已重启，并贴出晚于源码 mtime 的启动时间与启动成功日志行（R5）
- [ ] `curl -s http://127.0.0.1:3000/ | grep -o 'app.js?v=[0-9]*'` 的版本号随 `touch public/app.js` 变化（R6）
- [ ] `/app.js` 响应头是 `no-store`，`/vendor/` 才是长缓存；升级组件库未原地覆盖同名文件（R7）
- [ ] `data-shoelace` + `setBasePath` 双保险在位，E2E 外部域名请求为 0（R8）
- [ ] `server.listen()` 之前的每处引导调用都在 try/catch 内；清空 `shipments` + ERP 不可达时进程仍监听（R9）
- [ ] `npm test` 通过且输出里 `skipped 0`；本机局域网地址访问 `/api/health` 取不到 `demoAccount`（R10）
- [ ] 生产 `.env` 已写 `APP_USERNAME` / `APP_PASSWORD`；未登录访问 `/api/admin/settings` 返回 401（R11）
- [ ] `grep -rn 'catch\s*{' src/*.mjs` 无静默空 catch；启动与定时同步的 `failures` 都会进 `data/server.log`（R12）
- [ ] 改过默认值的配置项已回读核对，写入用的是完整 key，`saved` 不为 0（R13）
- [ ] 只提交部分配置卡片能保存成功；敏感字段 `null` 能清空、`''` 保持原值（R14）
- [ ] 诊断脚本带 `readOnly: true`；写库脚本有 `VACUUM INTO` 快照或 dry-run，且不与服务共用一个库文件（R15）

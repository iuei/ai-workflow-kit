# 让服务端改动真正生效

## 核心法则

**改了磁盘 ≠ 改了用户看到的东西。** 服务端改动要穿过四道门，任何一道没走完，用户看到的都和改之前一模一样：

```
改代码 → ① 进程重启 → ② 配置/迁移应用 → ③ 缓存失效 → ④ 存量数据回填
```

这是本机 194 个会话复盘里**最高频的摩擦**：「服务中断 / 反复启动」出现 73 次、跨 6 个项目；
项目文档里「重启」这个词出现 49 次（案例 P3）。

## 一、改完必须能证明「新代码在跑」

- 重启实例，并在交付说明里贴上**启动日志的时间戳**——没有新时间戳，等于没生效。
- 判据：`tail -3 data/server.log` 的启动时间晚于你的改动时间。
- 常驻进程（launchd / pm2 / 容器）要确认重启的是**同一个实例**：不要一边留着旧进程、一边新开端口
  （案例 P5：注册自启前先停手动实例，否则抢端口导致无限重启）。

## 二、四道门逐一确认

| 门 | 要确认什么 | 怎么查 |
| --- | --- | --- |
| ① 进程 | 新代码在跑 | 启动日志时间戳；接口返回里带版本号 |
| ② 配置 / 迁移 | 新配置与新表结构生效 | 配置页回显；`PRAGMA table_info(表名)`；迁移是否真的执行过 |
| ③ 缓存 | 前端拿到新资源 | 资源 URL 是否带新版本号；强刷后是否变化（案例 P3：`?v=<mtime>` + 页面显示版本） |
| ④ 存量数据 | 旧数据按新口径重算或回填 | 抽一条老记录走一遍新逻辑；算一遍新旧口径的差 |

**第②门的四个语义陷阱**（案例 P4，逐条对照）：

- 局部补丁式校验：只校验传来的字段，缺少的字段不报错
- 没有显式清空：想清空只能"不传"，于是永远清不掉
- 默认值 ≠ 存量值：改了默认值，库里旧记录不会变
- key 不完整：配置项路径拼错后静默失效

## 三、数据类改动先在副本上验证

清库、重拉、迁移、批量覆盖之前，用副本库 + 临时端口跑一遍（案例 T3 / P5）：

```bash
cp data/app.sqlite .probe/test.sqlite
DATABASE_PATH=./.probe/test.sqlite PORT=3211 node src/server.mjs &
# 验证通过后再对生产执行；用完 kill 掉临时实例并删副本
```

**禁止拿生产库试错**：真实事故里在生产库反复试密码，触发该账号锁定 15 分钟。

## 常见错误

| 错误 | 实际 |
| --- | --- |
| 「我改了 src/，所以好了」 | 用户连的是旧进程 |
| 「测试全绿」 | 测试跑的是新代码，用户用的是旧实例 |
| 「重启过了」 | 没有日志时间戳就不算证据 |
| 「配置我加上了」 | 存量记录不会因默认值变化而改变 |
| 「新开一个端口验证一下」 | 验证的不是用户正在用的那个实例 |

## 红牌

- 准备说「已完成」，而服务端改动后**没有重启**
- 交付里没有启动日志时间戳
- 只有一个实例的项目里，用「另起一个端口」代替重启
- 改了默认值或口径，却没检查存量数据

## 与其它技能的分工

- 前端 / UI 的取证：用 `verifying-ui-changes-in-browser`
- 失败的可观测性：用 `never-swallowing-failures`

# 用真实运行的实例验收改动（不是"我改了代码"）

## 核心法则

**没在用户会用的那个入口、那个角色、那个视口上跑一遍并量到证据，就不能说改动做完了。**

代码改对了 ≠ 用户看到了。中间隔着四道门：**跑起来没有**、**资源更新没有**、**规则命中没有**、**分支走到没有**。

本机 7 个项目 / 1152 条真实用户消息里，跨项目复现次数最多的摩擦就是这一条：
「并未实现统一」「多个页面没有生效」「团队知识库修改并没有生效」「为什么我昨天修改的用户数据没有同步，今天重启服务后依然是修改前的信息」。

而代价是可量化的：用户为此产生了 **80 条"是否已经完成"的追问**和 **186 条纯确认/推进消息（占全部消息 16%）**——**用户在被迫充当验收器**。

## 一、先跑起来：改动要作用在"用户会打开的那个实例"上

- 改了服务端（接口 / SQL / 配置）→ **重启实例**并确认新进程已起（看启动日志时间戳），否则用户看到的还是旧行为
- 改了前端 → 确认浏览器拿到的是新资源（资源 URL 带版本号、或强刷）
- 有常驻/守护进程（launchd、pm2、容器）→ 确认重启的是**同一个实例**，不是又开了一个端口
- 交付话术里写清"现在生效了"还是"需要重启才生效"

## 二、多分支矩阵：一次改动要在所有分支上验

界面上任何"看起来只有一种样子"的地方，往往有多个分支。**只在其中一个分支验证，等于没验证。**

| 维度 | 本机踩过的实例 |
| --- | --- |
| 角色 / 权限 | 只在管理员账号验证侧栏 → 普通用户走的是另一套框架，改动对他完全没生效（真实原话诊断：「你当前账号是普通用户…因此之前的侧栏样式没有生效」） |
| 视口 | 桌面正常，375px 下品牌被压成竖排、导航溢出被截断 |
| 状态 | 折叠 / 展开、空数据 / 满数据、加载中 / 失败 |
| 入口路径 | 整页渲染有样式，**局部刷新路径没更新**；列表能改，详情页没改 |
| 页面 / 模块 | 「只改了一处」——同一类改动散落在多个页面时必须全量扫 |

**同类点全量扫描**：一处不对，就主动把所有同类位置列出来逐个核销，而不是等用户发现第二个。
真实原话：「已经出现了两个类似问题了，全面检查是否还有其他地方有这种问题」。

## 三、「没变化」的三类根因，按这个顺序排查

**1. 生效层：改动根本没到用户眼前**
- 服务没重启（改了 `src/db.mjs` 这类服务端代码，跑着的还是旧进程）
- 资源被缓存；静态资源版本号只覆盖了部分文件，新增的 CSS/JS 没进版本号计算
- 部署/同步没做（改了本地，服务器上还是旧包）

**2. 命中层：改动到了，但没作用到那个元素**
- 规则被更具体的规则覆盖（同一选择器被写了四遍、新旧层叠加）
- 选择器不匹配（类名错了、元素在 shadow DOM 里、`::part` 不支持的写法）
- 组件内部结构假设错误：多个元素塞进同一个插槽、以为组件内部是 flex 容器
- 祖先属性改变定位基准：`backdrop-filter` / `transform` / `filter` 非 none 的祖先会成为 `position: fixed` 后代的包含块
- 组件行高由 CSS 变量推导（`--sl-input-height-*`）：只写 `height` 不写变量，文字会把容器撑高

**3. 分支层：走了另一条路**
- 角色 / 权限分支、媒体查询、特性开关
- 事件委托绑在的容器在重绘后换了，新节点不在委托范围内
- 口径不同：同一件事在"卡片统计"和"列表筛选"里用了两个条件（实测卡片 15 票 / 列表 173 票）

## 四、证据形态：可测量，而不是目测

```js
// 在真实浏览器里取几何与样式，而不是读代码推断
const el = document.querySelector('.sidebar');
const r = el.getBoundingClientRect();
return { width: Math.round(r.width), x: Math.round(r.x),
         lineHeight: getComputedStyle(el.querySelector('.account-text')).lineHeight };
```

- 几何：`getBoundingClientRect()`（宽度、位置、是否溢出、是否垂直居中）
- 样式：`getComputedStyle()`（实际生效值，能抓到"被覆盖"与"行高异常"）
- 截图：改前 / 改后各一张，关键区域裁剪
- 交互：真实点击、键盘（Tab / Esc / Enter）、焦点落点
- 对比度：前景/背景算比值（正文 ≥4.5:1，图形 ≥3:1）
- 请求：筛选、翻页后的实际请求参数与响应条数
- 持久化：刷新一次、重启一次再看数据还在不在

**把这些固化成可复跑的探针脚本**（放在 `.probe/` 之类目录），而不是一次性手测——下次改同一块时，同一份脚本直接给出前后对比。

## 五、对照用户原话逐条核销

用户列了 3 条要求，就回 3 条：每条给出证据，未做到的明说"没做/没验"。
不要用"已优化完毕"覆盖没做完的部分。

## 常见错误

| 错误 | 实际 |
| --- | --- |
| 「我改了代码所以好了」 | 用户看的是运行中的实例，不是磁盘 |
| 「我本地看过了」 | 你用的是哪个角色、哪个宽度、哪个状态？ |
| 「样式写了对齐」 | 量过 boundingBox 吗？"看起来对"在换行后会错位 |
| 「测试全绿」 | 单元测试不覆盖 DOM、CSS 层叠、角色分支与进程状态，全绿也挡不住这类回归 |
| 「改一处就够了」 | 同名规则/同类页面可能有多处 |
| 「用户没说就是没问题」 | 用户不是验收器；主动核销是交付的一部分 |

## 触发本 skill 的信号

- 用户说：没有变化 / 还是没生效 / 只有一处生效 / 刷新后还是旧的 / 没有成功 / 显示不对 / 不对齐 / 被挤高 / 服务又断了
- 你正准备说「已完成」，而这次改动涉及：CSS 或组件插槽、响应式、角色或权限分支、缓存资源、需要重启的进程、多处同类页面

## 四、收尾：让运行中的实例真正生效

- 改了服务端 → 重启实例并确认新进程已起来（看启动日志时间戳）

- 给用户的验证步骤要能照做：「刷新 → 点 X → 应该看到 Y」
